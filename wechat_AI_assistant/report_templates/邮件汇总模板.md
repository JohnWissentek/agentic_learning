# 邮件汇总标准模板与发件/收件/抄送角色推断规范（v1.0）

> **定位**：本文件与 [早间工作报告.md](早间工作报告.md)、[task_card_schema.json](task_card_schema.json) 共同构成统一的项目管理单一真理源（Single Source of Truth）。  
> **核心原则**：大模型分析每小时邮件批次后，**严格先产出符合 [task_card_schema.json](task_card_schema.json) 的标准 JSON**，再由确定性模板渲染成下方微信汇总消息；**绝不让模型自由发挥散文格式**。

---

## 一、发件人 / 收件人 / 抄送（`From / To / Cc`）角色自动推断规则

拉取邮件时，系统必须把每封信的 **`From`（发件人）、`To`（主送）、`Cc`（抄送）、`conversationId`（邮件会话号）** 一并结构化送入分析模型，按以下规则精准区分「谁负责、谁实施、谁只是知情抄送」：

> **域名分组**（在 `config/mail_domains.json` 中区分）：
> - **内部域名**：`palmarytech.com`、`wissentek.com`（其中 `john.xu@palmarytech.com` 为董事长本人）
> - **外部协作域名**：`budi.de`、`vandf.com`、`tera-instruments.com` 等合作方

| 序号 | 邮件头关系（`From` / `To` / `Cc`） | 董事长本人角色 | 自动推断的责任分工与建卡策略 |
| :-: | :--- | :---: | :--- |
| **1** | **外部 → `To` 内部同事（如王楠），`Cc` 董事长** | **知情监督（CC）**<br>⛔ 绝非执行人 | • `assignee`（实施人）= 主送栏内部同事（如王楠）<br>• `owner`（负责人）= 若正文点名某同事主导则填该同事，否则填主送内部同事或 `【待补齐】`（**严禁因被抄送就把董事长填成负责人或实施人**）<br>• `external_partner` = 外部发件人<br>• 策略：优先归为「团队跟进/外部协作任务」或追加已有任务时间轴，不塞进董事长个人待办 |
| **2** | **内部同事 → `To` 外部客户，`Cc` 董事长** | **知情监督（CC）**<br>⛔ 绝非执行人 | • `assignee`（实施人）= 内部发件同事（如王楠）<br>• `external_partner` = 外部主送方（如 Arnab/Budi）<br>• 策略：属团队对外沟通留痕 → **优先追加到已有在途任务的时间轴**；无对应任务时仅作「📌 团队进展同步」一句话知会，不乱建董事长待办 |
| **3** | **外部 → 直接 `To` 董事长**（未主送其他同事，或正文明确点名请董事长拍板） | **直接负责人 / 拍板人** | • `owner`（负责人）= 徐宏玮（本人）<br>• `assignee`（实施人）= 若为高层拍板/报价决策填 `本人`；若为具体执行且 `Cc` 了同事，标 `【待补齐（可交办给抄送同事 XX）】`<br>• `external_partner` = 外部发件人 |
| **4** | **内部同事 → `To` 董事长**（请示审批、汇报问题） | **拍板负责人** | • `owner`（负责人）= 徐宏玮（本人）<br>• `assignee`（实施人）= 发件同事（具体跑腿执行人）；在卡点中注明“待董事长批复” |
| **5** | **董事长发出（`From = 本人`）→ `To` 同事或外部** | **交办人 / 回复人** | • 发给内部同事：`owner` = 徐宏玮，`assignee` = `To` 栏同事<br>• 发给外部客户：`external_partner` = 外部主送，`assignee` = `Cc` 内部同事（若有）或本人<br>• **发件自动串线**：只要 `conversationId` 命中已有任务卡，直接自动追加为该卡时间轴记录（不新建任务、不建确认卡） |

## 二、邮件往来自动串线与防重 3 条铁律

1. **老任务自动追加时间轴（`task_updates`），绝不建重复卡**：
   - 先用微软 Graph 原生 `conversationId` 精确匹配已有在途任务卡；未命中时再用语义匹配在途任务。
   - 命中后，把本时段收发邮件压缩成带时间戳的一句话追加进该任务卡的 **`2）当前进度与往来沟通`**（格式：`[MM-DD HH:MM｜邮件收/发｜谁→谁] 一句话事实`）。**老任务字段已齐全，无需再打扰老板补必填项。**
2. **真正新事只建 1 张独立任务卡（`new_tasks`）**：
   - 同一物理事项的多封来回邮件（例如 Budi 的 Arnab 与 Martin 讨论同一件事），合并成 **1 张独立任务卡**（严禁拆成“我回复对方”+“我等对方回复”两张碎片卡）。
   - 邮件缺失必填项（归属项目 / 实施人 / 目标截止日）时，**绝不瞎猜当天或胡套无关旧项目**，显式标为 `【待补齐】` 并提示补全。
3. **纯知会/团队同步（`fyi_notices`）**：
   - 未命中已有任务、且无需董事长出手的抄送邮件，只列一句带时间戳的同步摘要，不建冗余任务卡。

## 三、《邮件汇总》标准微信输出模板

```text
📧 邮件汇总（HH:MM[，含此前未推送的邮件]）

📋 确认 #<proposal_id>｜<本批核心标题（严禁重复“确认 #N”前缀）>

【一、拟新建独立任务卡】（无则隐藏本节）
▸ 新任务 1：<任务名称>（归属：<项目名或【待补齐】> / <板块>｜<优先级>）
  1）目标与交付成果：<最终可验收硬结果>
  2）当前进度与往来沟通：
     - [MM-DD HH:MM｜邮件｜From→To(抄送:Cc)] <一句话核心事实>
  3）责任分工：负责人：<按From/To/Cc推断或【待补齐】> ｜ 实施人：<推断或【待补齐】> ｜ 外部协作：<外部联系人>
  4）时间排期：开始 <YYYY-MM-DD> → 目标截止：<YYYY-MM-DD 或 【待补齐】>
  5）卡点与关联档案：<待决策/待对方回复点> ｜ 会话已自动绑定

【二、拟追加到已有在途任务的往来沟通】（不新建卡，无则隐藏本节）
- 归入 任务 #<task_id>《<已有任务名>》：
  ↳ [MM-DD HH:MM｜邮件｜From→To] <一句话进展/回复内容>（状态更新：<保持/建议变更>）

【三、纯知会与团队进展同步】（不建卡，无则隐藏本节）
- [MM-DD HH:MM｜抄送知会｜From→To] <一句话内容>

【四、你发出 N 封（不建卡）】（无则隐藏本节）
- HH:MM 发给 <对方邮箱>｜<主题>[｜已自动归入 #<task_id>][｜可能在等对方]

⚠️ 缺失必填提示（有【待补齐】项时显示）：
- 新任务 1 缺少：<具体缺失的必填字段名>
👉 回复 1 确认落盘 ｜ 2 仅存想法 ｜ 0 作废 ｜ 改：<补全或调整意见> 重算
```

### 其余两种整点运行分支（无需建确认卡）

- **分支 B：本时段仅有您发出的邮件（无新收件）** → 零大模型调用、不出确认卡；命中已有任务会话的发件自动归入时间轴：
  ```text
  📧 邮件汇总（HH:MM）

  你发出 N 封（不建卡）：
  - HH:MM 发给 <对方邮箱>｜<主题>[｜已自动归入 #<task_id>][｜可能在等对方]
  ```
- **分支 C：已有未回复的待确认卡（防覆盖顺延）** → 本班暂不对新收件出新卡、不推进收件水位，待您处理旧卡后下一班自动分析；同时正常推送并归入您发出的邮件：
  ```text
  📧 邮件汇总（HH:MM[，含此前未推送的邮件]）
  这小时有 M 封收件：<主题 1>；<主题 2>。
  确认卡 #<pending_id> 还没回复，本班不生成新卡。回复 1、2 或「改：…」之后，下一班再分析这些收件。

  你发出 N 封（不建卡）：
  - HH:MM 发给 <对方邮箱>｜<主题>[｜已自动归入 #<task_id>]
  ```

## 五、对应的标准 JSON 交互契约

大模型输出必须严格遵守 [task_card_schema.json](task_card_schema.json) 中的 `$defs.UnifiedTriageProposal`（与微信路径④共用同一套契约），核心字段一览：
- `headline`：纯净标题（不含 `确认 #N` 前缀）
- `new_tasks[]`：每项都是标准 `TaskCardDraft`（含 `role_inference_reason` 说明从 `From/To/Cc` 推断的依据，及 `missing_required_fields[]`）
- `task_updates[]`：匹配到已有 `task_id` 的时间轴追加条目（`timeline_entry` + 可选 `blocker_note` 更新）
- `fyi_notices[]`：纯抄送知会条目（不建卡）
- 微信文案与数据库落盘均严格基于这份 JSON 确定性执行。
