## 1. 结论

第一期到第三期采用这条链路：

```text
个人微信
  → 企业微信「微信插件」里的智能机器人
  → 服务器上的一条 WebSocket 长连接
  → 片段器：把连续到达的消息合成一个片段
  → 阿里云百炼 qwen3.8-max：切分话题，标领域、类型、标签
  → 自有数据库和文件目录
  → 机器人把回执和每日清单推回个人微信
```

系统只产出三样东西：待办清单、对话记录、自动存档（摘要文档和附件）。不连接 Odoo 或其他业务系统。

这条链路官方支持，服务器不必有公网回调地址。机器人只接收发给它的单聊，以及群里 @它的消息。个人微信中的其他会话不会进入这条链路。

全自动读取「本人与客户的个人微信原会话」没有官方接口。那不是实施时再想办法绕过的问题，而是产品边界。自动拉取只在以后另开一期时考虑，并且只针对已经走企业微信外部联系人、并开通会话内容存档的会话。

## 2. 三条路线

| | 路线 A：智能机器人长连接 | 路线 B：会话内容存档 | 路线 C：非官方个人微信接口 |
| :--- | :--- | :--- | :--- |
| 能收到什么 | 发给该机器人的消息 | 开通范围内，员工与微信外部联系人的会话 | 声称能读个人微信会话 |
| 个人微信里怎么用 | 微信插件关注后，在「我的企业」里找到机器人 | 对方用微信，本人用企业微信身份聊天 | 不在本文范围 |
| 是否自动覆盖现有个人微信聊天 | 否。需要转发或直接发给机器人 | 否。只覆盖外部联系人会话，且需对方同意 | — |
| 服务器要求 | 一台常开机器，主动连 `wss://openws.work.weixin.qq.com` | 企业微信数据与智能专区、公钥、专区程序 | — |
| 费用与权限 | 企业微信可个人免费注册。API 模式在公司企业里可能要管理员 | 单独开通的付费能力；员工告知；外部联系人同意 | 违反平台规则，有封号风险 |
| 本文决定 | **前三期采用** | 以后另议 | **不做** |

路线 A 还有一种更老的做法：自建应用加「接收消息」回调，再配企业可信 IP。它同样只能收到发给该应用的消息，还要求公网 URL。长连接已经覆盖同一能力，不采用回调方案。

## 3. 路线 A 的官方限制

实施时按这些限制设计，不把它们当成故障。

- 每个机器人同时只能有一条有效长连接。新连接会踢掉旧连接。服务做成单实例，断线后重连，不做多实例同时订阅。
- 连接建立后发送订阅命令 `aibot_subscribe`，凭证是 BotID 和长连接 Secret。Secret 与回调模式的 Token、EncodingAESKey 不是同一个。
- 需要心跳，间隔约 30 秒。
- 单聊可收文本、图片、图文混排、语音、文件、视频。语音回调里已是转写文本。群聊只收 @机器人的文本和图文。
- 主动推送使用 `aibot_send_msg`。用户先在该会话里发过消息之后，定时清单才能推回去。
- 同一条消息可能重复回调。用 `msgid` 去重。
- 微信插件的入口在企业微信管理后台「我的企业 → 微信插件」。个人微信扫描「邀请关注」后，才能在个人微信里看见这个企业及其机器人。

### 3.1 未写进官方文档、必须实测的行为

对应需求说明第 3.1 节 T1–T3。实测前不要假设下面任何一项成立：

- 「聊天记录」（合并转发）卡片能否到达、回调里是什么 `msgtype`、是否带每条的原发送人和原时间。
- 逐条转发时，每条之间的到达间隔分布（决定静默时间取值）。
- 逐条转发的消息是否带原发送人；不带时，回调里的发送人都是本人。

第一步做连接器时，就把每条回调的**完整原始结构（去掉正文后）**记进开发日志，用来回答上面三个问题。正文不进日志，见第 10 节。

## 4. 系统结构

```text
个人微信 / 企业微信客户端
        │  发给机器人
        ▼
连接器（一个进程）
  维持 WebSocket、心跳、断线重连、msgid 去重
        │
        ▼
收件库
  每条原文、附件、处理状态
        │
        ▼
指令识别 ──是指令──→ 回复与日程（完成 / 忽略 / 改领域 / 拆开 / 并到上一段 / 查）
        │不是指令
        ▼
片段器
  按静默时间把连续消息合成片段；「好了」立即结束片段
        │片段收齐
        ▼
分析器
  组装片段 + 近期上下文 + 已知标签，调用 qwen3.8-max，校验 JSON
        │
        ├── 条目库（每个话题一条：领域、类型、标签、摘要）
        ├── 待办库
        └── 标签库
        │
        ▼
存档器
  对话记录、摘要文档、附件写入 data/archive/日期/领域/
        │
        ▼
回复与日程
  片段回执；工作日定时清单；查找
```

| 部分 | 职责 | 不负责 |
| :--- | :--- | :--- |
| 连接器 | 长连接、心跳、收消息、发回执和清单 | 不调用模型，不判断片段 |
| 收件库 | 按 `msgid` 落原文和附件，记录处理状态 | 不理解语义 |
| 指令识别 | 判断一条消息是不是短指令 | 不分类工作内容 |
| 片段器 | 把消息合成片段、决定何时收齐 | 不按话题切分（交给分析器） |
| 分析器 | 判断意图、切分话题、判断以前有没有、分类、抽待办。内部是 LangGraph 的片段处理图，见 [05-片段处理图.md](05-片段处理图.md) | 不直接给微信发消息；模型节点不写数据 |
| 条目 / 待办 / 标签库 | 保存分析结果，按来源去重 | 不保存密钥 |
| 存档器 | 把对话原文、摘要、附件写成可直接浏览的文件 | 不调用模型 |
| 回复与日程 | 把结果写成短回复，到点推送清单，执行指令。纠正、问答、规则提议、固定指令、每日清单见 [06-纠正查询与清单.md](06-纠正查询与清单.md) | 不自己分类，需要重新分析时调用分析器 |

## 5. 片段：合并与切分的实现

对应需求说明第 8.2 节。

### 5.1 片段的状态

| 状态 | 含义 |
| :--- | :--- |
| 收集中 | 还在接收消息，每来一条就刷新「最后一条时间」 |
| 已收齐 | 静默超时、本人发「好了」，或收到的是一张合并转发卡片 |
| 已分析 | 模型结果已落库 |
| 分析失败 | 可重试，原文不丢 |
| 已合并 | 被「并到上一段」并入另一个片段，只保留指向目标片段的记录 |

### 5.2 合并（片段器）

1. 一条非指令消息进来，查同一会话里有没有「收集中」的片段。有就加入，并把该片段的「最后一条时间」改为现在；没有就新建一个片段。
2. 一个定时任务每 5 秒扫一次：「收集中」且 `最后一条时间 + 静默时间 ≤ 现在` 的片段改为「已收齐」，送分析器。
3. 静默时间默认 60 秒，放在配置里，按实测的逐条转发到达间隔调整（取实测最大间隔的 3–5 倍）。
4. 合并转发卡片（若实测可用）单独成片段，直接「已收齐」，不等计时。若此时有「收集中」的片段，先把它收齐。
5. 片段状态和时间都存在数据库里，不放在内存。进程重启后，定时任务照常扫描，不会丢片段。
6. 片段收齐时回复一次「已收到 N 条，正在整理」，不对每条单独回执。

### 5.3 本人备注

片段里本人亲手写的说明（如「这是 A 项目的」）要优先采信。逐条转发如果不带原发送人，服务器无法从结构上区分「转发来的」和「本人写的」，因此：

- 支持可选前缀「备注：」，带前缀的消息在片段里标为本人备注。
- 不带前缀时，提示词要求模型把片段末尾的、用第一人称口吻对整段做说明的短句视为本人备注，并在输出里标出它认定的备注，便于回执里核对。

### 5.4 切分与关联（分析器）

- 模型对一个片段输出一个或多个**条目**，每个条目对应一件事，带自己的领域、类型、标签和来源消息范围。
- 提示词附上最近 3–5 个已分析片段的摘要和标签。模型判断新片段与其中某个是同一件事时，输出 `related_segment`，系统只通过标签关联，不改动旧片段；`related_confidence` 不高时，回执里问「需要合并到上一段吗」。

### 5.5 纠正指令

| 指令 | 处理 |
| :--- | :--- |
| 「好了」「完」 | 当前「收集中」的片段立即收齐 |
| 「拆开」 | 对最近一个已分析片段重新调用模型，提示词要求按话题更细地切分 |
| 「并到上一段」 | 最近一个片段标为「已合并」，消息并入前一个片段，对合并后的片段重新分析 |
| 「改成 <领域>」「3 改成 <领域>」 | 改对应条目的主领域，不重新调用模型；存档文件移到新领域目录 |
| 「查 <名称>」 | 按标签（含别名）查最近 10 条记录和未完成待办，只回标题、日期、领域 |

重新分析时，旧条目标为「已替换」，不物理删除。新生成的待办与旧待办按标题相似度对应，已完成或已忽略的状态保留，不重复生成。

收到指令时如果有「收集中」的片段，先把它收齐，再执行指令。

### 5.6 指令识别规则

- 只把**整条消息**与指令表精确匹配或用简单正则匹配（如 `^完成\s*\d+$`）。不在长文本里找指令词。
- 「好的」「收到」之类不是指令，按普通消息进片段。

## 6. 一条消息怎么走

1. 连接器收到 `aibot_msg_callback`。`msgid` 已存在则直接结束。
2. 原文和附件写入收件库，状态为「已收到」。
3. 指令识别。是指令就交给回复与日程处理，流程结束。
4. 不是指令，交给片段器加入片段（见 5.2）。
5. 片段收齐后，回复「已收到 N 条，正在整理」。
6. 分析器组装输入：片段内全部消息（按到达顺序，附件以文件名占位）、近期片段摘要、已知标签清单、领域和类型定义。调用模型。
7. 模型输出必须是合法 JSON 并通过结构校验。不合格时片段状态改为「分析失败」，回复本人可以稍后重试。原文保留。
8. 每个条目写入条目库；置信度达到阈值的待办写入「未完成」，不足的写入「待确认」；标签按 8.1 归并。
9. 存档器写文件：片段原文写成对话记录；类型含「记录」的条目写成摘要文档；附件移入存档目录（见 8.2）。
10. 回复：分成几条、每条的领域和标签、待办标题、待确认原因、可能相关的上一段。回复要短，详情以服务器上的记录为准。
11. 片段状态改为「已分析」。

## 7. 模型

使用阿里云百炼，北京地域，OpenAI 兼容接口。

| 项 | 值 |
| :--- | :--- |
| 模型 ID | `qwen3.8-max` |
| 固定快照 | `qwen3.8-max-0902`（行为要锁死时再用） |
| Base URL | `https://dashscope.aliyuncs.com/compatible-mode/v1` |
| 鉴权 | 环境变量中的百炼 API Key，请求头 `Authorization: Bearer ...` |
| 中国内地参考价 | 输入 12 元 / 百万 Token，输出 36 元 / 百万 Token，上下文 100 万 Token |

价格以百炼价格页当时显示为准：<https://help.aliyun.com/zh/model-studio/model-pricing>。模型列表：<https://help.aliyun.com/zh/model-studio/models>。

### 7.1 调用约定

- 只让模型输出 JSON，不让它决定要不要发微信或写文件。
- 温度取低值，保证同一段话多次分类接近。
- 提示词里写明七个领域加「其他」的定义和判断原则（归最终负责交付的那一块）、四种类型、标签种类、各领域必抽字段，以及「没有的数字不要编」。
- 领域和类型用固定代码，提示词和校验共用一份定义，避免中英文写法不一致：

| 代码 | 领域 |
| :--- | :--- |
| `sales` | 客户与销售 |
| `delivery` | 项目交付与售后 |
| `rnd` | 产品研发 |
| `supply` | 采购与生产 |
| `finance` | 财务与法务 |
| `hr` | 人事行政 |
| `it` | IT 与信息化 |
| `other` | 其他 |

类型代码：`todo`（待办）、`record`（记录）、`decision`（决定）、`unsure`（待确认）。

- 单次输入控制在一个片段加上有限上下文。不把全部历史一齐送入。
- 语音用企业微信已经转好的文字，不再单独调用语音识别。
- 图片先保存。第三期若需要理解图中文字，先在百炼模型卡片上确认 `qwen3.8-max` 的视觉能力是否覆盖该输入；不够再用百炼当时的视觉模型，不在文档里预设第二个模型 ID。

```json
{

    {
      "source_msg_range": [1, 6],
      "domain": "sales",
      "sub_domain": "delivery",
      "types": ["todo", "record"],
      "tags": {
        "customer": ["某某科技"],
        "project": ["某某二期"],
        "product": [],
        "supplier": [],
        "person": ["王经理"]
      },
      "fields": { "contact": "王经理", "amount": "原文中的金额", "stage": "报价", "next_step": "原文中的下一步" },
      "summary": "两三句话的摘要，数字保留原话",
      "todos": [
        { "title": "按约定日期回复方案", "owner": "本人", "due": "2026-11-05", "confidence": 0.9 }
      ],
      "decision": null,
      "confidence": 0.85,
      "uncertain_reason": null
    }
  ],

```

字段缺失、领域或类型代码不在表内、`source_msg_range` 越界，都按校验失败处理。

API Key、BotID、Secret 放在服务器环境变量或服务器本地的环境文件中。仓库已忽略 `.env`、`.env.*` 和文件名中带 token、secret 的文件。这些值不进入 Git。

## 8. 存什么

数据库用 SQLite 即可。一个人的消息量不需要先上独立数据库服务。以后要搬再迁。

| 表 | 主要字段 | 约束 |
| :--- | :--- | :--- |
| 消息 `messages` | `msgid`、会话、方向（收 / 发）、发送人、消息类型、文本、附件编号、收到或发出时间、所属片段、是否本人备注、处理状态 | `msgid` 唯一。机器人发出的回执、提问、清单也记一条，方向为「发」 |
| 片段 `segments` | 会话、状态、开始时间、最后一条时间、收齐方式（超时 / 指令 / 卡片）、合并目标 | 同一会话同时最多一个「收集中」 |
| 条目 `items` | 所属片段、来源消息范围、主领域、次领域、类型、摘要、抽取字段（JSON）、置信度、不确定原因、是否已替换 | — |
| 待办 `todos` | 所属条目、标题、负责人、截止时间、领域、状态 | 同一片段加相似标题不插第二次 |
| 存档 `archives` | 所属片段或条目、种类（对话记录 / 摘要文档 / 附件）、领域、相对路径、生成时间 | 相对路径唯一 |
| 标签 `tags` | 种类（客户 / 供应商 / 人）、标准名 | 种类 + 标准名唯一。项目和产品改为对象，见 [09-对象清单.md](09-对象清单.md) 第 8 节 |
| 标签别名 `tag_aliases` | 别名、指向的标签、是否本人确认过 | 别名 + 种类唯一 |
| 条目标签 `item_tags` | 条目、标签 | — |

### 8.1 标签归并

- 模型输出的标签名先查别名表。命中且本人确认过，直接归到对应标签。
- 没命中但与已有标签相似（包含关系或编辑距离很小），记为待确认别名，在回执或清单里问一次「××是不是××」；本人确认后写入别名表，以后自动归并。
- 完全新的名称直接新建标签。

### 8.2 存档目录

存档是普通文件，不依赖数据库也能直接浏览、备份和全文搜索。规则以 [00](00-工作流设计系统提示词.md) 第 3.6 节为准：原件库和归档分开，归档按「日期 / 领域 / 事项」组织。

```text
data/
  inbox/                                   ← 原件库：收到即存，永不移动、永不修改
    2026-10/
      <msgid>.jpg / .pdf / ...             ← 附件原文件，按内容哈希去重
  archive/                                 ← 归档：浏览视图，文件是指向原件的硬链接
    2026-10-31/
      当日完整对话.md                       ← 当天机器人会话的全部消息，双向，含指令、回执、提问、作答
      sales/
        0931-某某科技-二期报价/             ← 一个事项一个文件夹
          对话.md                           ← 本事项的原文，按到达顺序，带时间、本人备注、附件链接
          摘要.md                           ← 标题、标签、摘要、原文摘录、待办、决定、附件清单
          图片/0931-01-现场照片.jpg
          图片/0931-01-现场照片.jpg.txt     ← 图中文字与描述（第三期）
          文档/0931-报价单V3.pdf
          文档/0931-报价单V3.pdf.txt        ← 提取出的文字，进全文检索
          语音/0935-01.txt                  ← 企业微信转写文本；能取到音频时一并保存
          视频/
      hr/
        ...
      other/
        0940-闲聊/对话.md                   ← 闲聊只有对话记录
      未归类/
        0950-片段1024/对话.md               ← 分析失败、整段待确认的片段
```

- 事项文件夹名：`时分-标题`，标题由模型给出，去掉文件系统不允许的字符；重名时加序号，不覆盖。附件文件名：`时分-序号-原文件名`。
- 附件跟着所在消息归事项：切分把哪段消息分给哪个事项，那段里的附件就进哪个事项文件夹。
- 一个片段切成多个事项、分属不同领域时，每个事项文件夹只放自己范围内的消息和附件；整段原文在当日完整对话记录里，各事项的对话记录链接过去。
- 同一文件重复发送：原件库按内容哈希只存一份，各事项文件夹各自链接。
- 改领域时移动事项文件夹，并更新 `archives` 表的路径。
- 重新分析（拆开、并到上一段）时，旧事项文件夹改名加 `.已替换` 后缀保留，按新结果重建。
- 本人要求删除时，原件、归档链接、提取文本和数据库记录一并删除。
- 数据库里只存相对路径。

`data/` 不提交到 Git。

## 9. 部署

一台常开的机器跑连接器、片段器、分析器和存档器，保证长连接不断。机器可以在内网，只要能访问企业微信和百炼。

部署目标定为阿里云 ECS `firematrix`（呼和浩特，Ubuntu 24.04，2 核 4 GB，2 Mbps 固定带宽不计流量，60 GB 系统盘）。与机器上已有的 FireMatrix 官网共存，本项目不占端口、不改安全组。具体操作见 [03-部署实施.md](03-部署实施.md)，连接信息在本地 `.env.ecs`。代码放 GitHub，`data/` 只在服务器上。

进程要求：

- 只跑一个连接器实例。
- 断线后按间隔重连，避免紧循环把订阅打到频率限制。
- 片段状态和分析队列都存在数据库里，进程重启后继续，不靠内存记进度。
- 时钟用北京时间。清单默认工作日 18:00，静默时间默认 60 秒，都做成配置。

企业微信侧的配置顺序：

1. 准备一个能创建 API 模式机器人的企业微信。公司企业开不了时，另注册一个只给本人用的企业。
2. 创建智能机器人，选择 API 模式、长连接，记下 BotID 和 Secret。可见范围只包含本人。
3. 在「我的企业 → 微信插件」用个人微信扫码关注。
4. 启动服务器上的连接器，确认订阅成功。
5. 在个人微信里给机器人发「你好」，确认收件库有记录且机器人有回复。

第 5 步通过之前，不接模型。先证明消息进得来、回得出去。

## 10. 安全

- 机器人可见范围只有本人。不把客户拉进这个机器人会话来「自动采集」。
- 长连接 Secret 和百炼 API Key 只放服务器本地。
- 日志记录 `msgid`、片段编号、状态和错误码，不记录消息全文。实测阶段记录的回调结构也要先去掉正文。
- 发给百炼的内容就是待分析的工作沟通。不另做一份带全文的调试日志。
- 存档目录只在服务器本地，按需加入本机备份；不放进 Git，不同步到公共网盘。
- 每日清单推回本人的个人微信。不推到群。

## 11. 实施顺序

每一步做完就能单独验证。上一步没通过，不开始下一步。

| 步骤 | 做什么 | 怎样算通过 |
| :--- | :--- | :--- |
| 1 | 企业微信机器人长连接，个人微信发文本 | 收件库有一条，`msgid` 重复回调不产生第二条，机器人有回复 |
| 2 | 转发方式实测（需求说明 T1–T3） | 记下合并转发能否收到及其结构、逐条转发的到达间隔、是否带原发送人；据此定首选转发方式和静默时间 |
| 3 | 片段器和指令识别 | 逐条转发 8 条只生成 1 个片段、只回执一次；「好了」立即收齐；重启进程后收集中的片段仍能收齐 |
| 4 | 接入 `qwen3.8-max`，只处理文本片段 | 样例片段得到合法 JSON；前半段报价、后半段招聘被切成两条并归入正确领域；各领域样例分类正确 |
| 5 | 写入条目、待办、标签，存档器写对话记录和摘要，并做来源去重 | 同一段话发两次，正式待办和存档都只有一份；简称和全称经一次确认后归到同一标签；存档目录可直接浏览 |
| 6 | 纠正与查找指令：完成、忽略、改领域、拆开、并到上一段、查 | 清单状态改变；改领域后存档文件移到新目录；重新分析后已完成的待办不复活、不重复；「查」返回该标签的记录和待办 |
| 7 | 工作日 18:00 推送清单 | 个人微信收到按领域分组的未完成待办、今日新增存档、今日决定、待确认 |
| 8 | 图片、文件、语音转写 | 附件自动进入存档目录并可取回；摘要不出现原文没有的数字；语音按转写文本分类 |

步骤 1 到 7 对应需求的第一期和第二期。步骤 8 对应第三期。步骤 4–7 由 [08-选型与实施.md](08-选型与实施.md) 第 3 节的步骤 A–F 取代，以那里为准。

## 12. 以后另议

### 12.1 写入 Odoo 等业务系统

本期不做。以后要做时，先改需求说明，再在存档器之后增加一个独立的连接器，读取条目库和待办库，经本人确认后写入。条目里的领域、标签和抽取字段已经按公司职能组织，届时可以直接复用，不需要改动前面的收集和分析部分。

### 12.2 全自动收集

只有在工作沟通改成下面这样之后，才评估会话内容存档：

- 客户是企业微信里的微信外部联系人。
- 企业已开通数据与智能专区，应用配置了公钥。
- 员工被纳入存档范围，外部联系人已同意。

官方拉取接口只提供大约 5 天内的记录，所以要当天增量拉取并自己落库，不能等周末再拉。这一期与路线 A 的片段器、分析器、条目库、存档器可以共用，收集端换成存档同步；存档里的会话天然带发送人和时间，片段可以按会话和时间直接切分。前三期不实现这个收集端。

## 13. 不做的事

- 不实现个人微信协议接入、网页版微信、客户端内存读取或界面自动操作。
- 不登录、不写入 Odoo 及其他现有业务系统。
- 不使用自建应用的公网回调，除非长连接在目标企业里确实开不出来，并且需求说明已改。
- 不让机器人代替本人回复客户。
