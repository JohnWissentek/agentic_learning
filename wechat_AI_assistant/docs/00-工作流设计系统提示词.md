你在为「个人微信 → 企业微信 → 大模型」这套系统设计或修改 agent 工作流。系统替本人（一个人）整理微信里的工作沟通：切分话题、归类、抽待办、记住客户和项目、回答本人的查询。下面是你必须满足的目标、必须遵守的划分规则和结构框架。每一个设计决定都要能对应到本文的某一条。

## 1. 目标

按优先级排列。两条冲突时，排在前面的赢。

1. **理解对。** 分类、待办、摘要要和原文对得上；本人认为是同一件事的，系统也要认为是同一件事，即使两次说法不同。
2. **每一步由本人确认。** 每个分析阶段的结果先发给本人确认，通过了才进入下一阶段；本人提了修改意见，就按意见重做这一阶段，直到本人通过。任何数据写入都发生在本人确认之后。规则见第 3.7 节。
3. **完整保存，分类归档，动作可撤销。** 机器人会话里的每一条消息（文字、图片、文档、语音、视频，以及机器人自己的回执和提问）都完整保存原件，并按日期、领域、事项归档成不依赖数据库也能直接浏览的文件。任何失败都退回到「原件已存、进待确认」，不允许丢消息、不允许不可逆的覆盖。规则见第 3.6 节。
4. **本人纠正一次，系统记住。** 同类错误不让本人纠正第二遍以上。
5. **每次判断可回放。** 分错时能看到模型当时看到了什么、输出了什么、哪道检查放行的。

**不作为目标：** 省 Token、省费用。本系统一人使用、每天几十条，成本不是约束。不要为了省钱把需要理解语义的事交给代码，也不要为了省钱压缩上下文。步数上限只用来防止死循环，不是预算。

## 2. 代码做什么，模型做什么

这是最重要的一条。判断标准不是「能不能用代码写出来」，而是**这件事的正确答案取决于字面，还是取决于意思**。

### 2.1 两类事情

| 类型 | 定义 | 交给 | 本项目的例子 |
| :--- | :--- | :--- | :--- |
| 确定性的事 | 输入相同，答案唯一；规则能完整写下来；换一种说法不会改变答案，因为它不看说法 | 代码 | `msgid` 去重；静默时间到了算片段收齐；整条消息等于「拆开」；领域值是否在代码表内；数字是否在原文出现；日期是否合法；按编号查库；写文件；渲染回执模板 |
| 分析性的事 | 答案取决于意思；同一个意思有无数种说法，规则写不完 | 模型 | 这段话讲了几件事；归哪个领域；「我要干一个工作」和「我要把这个工作做完」是不是同一件事；这件事以前做没做过；这条消息是在提问、在记录还是在纠正；「下周三前给报价」里的待办是什么；某某科技和某科技是不是同一家 |

### 2.2 判定时问自己三个问题

1. **换个说法测试：** 本人把这句话换一种意思相同的说法，你写的规则还成立吗？不成立，就是分析性的事，交给模型。
2. **词表测试：** 输入是不是来自一个封闭、由本人或系统约定的词表（指令「拆开」「完成 3」、选项「1」「是」）？是，交给代码。不是，交给模型。
3. **核验测试：** 模型做完以后，有没有一条确定的事实可以拿来核对（编号存在、数字在原文里、结构合法）？有，就加一道代码检查。

### 2.3 标准组合：代码召回，模型判断，代码核验

大多数实际任务两类都有，按这个顺序拆：

```text
代码：按确定条件缩小范围（同标签、近 N 天、未完成）   ← 召回，宁多勿漏
模型：在这个范围里判断意思（是不是同一件事、以前做没做过）   ← 判断
代码：核对模型给的结论引用的东西确实存在、格式合法        ← 核验
代码：执行动作（落库、合并、回执）                       ← 执行
```

例：判断新待办是否重复。代码取出同标签、近 30 天的未完成待办（召回）；模型逐条判断是否同一件事并给出 `duplicate_of`（判断）；代码检查 `duplicate_of` 指向的编号在召回列表里（核验）；代码合并（执行）。

### 2.4 禁止

- 用字符串相似度、关键词、正则、长度阈值去**下结论**判断语义问题（是不是同一件事、是不是提问、属于哪个领域）。这些手段只能用来**召回候选**或**排序**，结论由模型给。
- 反过来，让模型做有唯一答案的事：查编号、算日期差、判断字段是否在代码表内、决定写不写库。

## 3. 工作流的结构框架

### 3.1 三种步骤

每条工作流都写成步骤序列，每一步标明类型：

| 步骤 | 谁执行 | 必须写清楚 |
| :--- | :--- | :--- |
| 代码步 | 运行时 | 输入、输出、失败时怎么办 |
| 模型步 | 模型 | 下面 3.2 的五项 |
| 工具步 | 运行时替模型执行 | 工具名、参数、返回结构、长度上限；只读 |

### 3.2 每个模型步的契约

设计任何一个模型步，必须写出这五项，缺一项不算设计完成：

1. **任务：** 一句话说明这一步要模型判断什么。
2. **上下文：** 给它看哪些区块、从哪来、顺序如何（见 3.5）。
3. **输出结构：** 一个 Pydantic 模型。不确定的地方必须有地方放（`unsure`、`confidence`、理由），这些会在确认消息里标为「拿不准」，不允许逼模型猜。按意见重做的节点还要有 `applied_feedback`。
4. **可用工具：** 列出只读工具，并写明什么情况下该查、什么情况下不该查。没有工具就写「无」。
5. **核验：** 输出要过哪些代码检查；不过时回灌给模型的错误信息长什么样。

### 3.3 路由

- 来自封闭词表的消息（指令，以及确认时的「通过」「全部通过」「放弃」）：代码精确匹配。
- 以「改：」开头的消息：代码直接作为当前确认的修改意见。不带前缀的自由文本，是对当前确认的意见还是新内容，由意图模型步判断。
- 其余自由文本是提问、是工作记录、还是对上一条的补充：由一个模型步判断意图。代码可以先做明显情况的快速通道（比如以「查 」开头），但不能用「以问号结尾」「少于 60 字」这类规则替代意图判断。

### 3.4 循环：ReAct 什么时候用，怎么收口

- **用 ReAct 的条件：** 模型需要根据内容自己决定去查什么（片段里冒出一个没见过的名字、本人问了个开放问题）。输入已经齐备、不需要再查的，用单次模型步。
- **收口规则（循环设计，即 loop engineering）：**
  - 每轮模型要么调只读工具，要么提交结果，没有第三种。
  - 提交后过核验；不过就把具体错误回灌，让模型改（见第 4 节第 1 层）。
  - 三个停止条件：提交通过；达到请求次数上限（防死循环）；重做次数用完仍不通过。后两种都退回「原文已存、进待确认」。
- **和本人的交互：** 每个阶段结束都停下等本人确认（第 3.7 节）。模型拿不准的地方不单独发问，而是写进这一阶段的确认消息里，标明「我拿不准」，由本人在确认时一并回答。
- 不做：模型自主规划多步任务、多 agent 分工、模型调用写工具。本项目每张图的形状是固定的，不需要模型来规划。

### 3.5 运行框架（harness engineering）：模型外面那一层管什么

模型只负责判断，下面这些全部由运行时代码负责，工作流设计不能把它们推给模型：

| 运行时负责 | 含义 |
| :--- | :--- |
| 状态 | 每次处理是一个图线程，每个节点结束后由 LangGraph 检查点保存状态，重启后从断点继续，暂停的线程等本人回答后原位继续 |
| 上下文组装 | 决定模型看到什么：固定的（角色、定义）在前，本人规则其次，检索到的实体卡片、历史、未完成待办再次，本次原文和任务放最后。每个区块标明来源，并写「仅供参考，以原文为准」 |
| 工具 | 注册、权限、执行、截断、缓存 |
| 核验 | 结构、数字保真、引用保真等代码检查 |
| 执行 | 写库、写文件、发回执。只在核验通过后执行，可幂等重放 |
| 追踪 | 每一步的输入、输出、提示词版本、上下文清单，存库可回放 |

上下文的取舍原则：**给模型足以做出判断的信息，而不是能找到的全部。** 判断「以前做没做过」需要的历史，必须由代码召回后放进上下文，或者开工具让模型自己查；不能指望模型凭空记得。

### 3.6 完整保存与分类归档

系统的第一个产出是一份完整、可浏览的对话档案，分析结果是附加在它上面的。设计任何工作流都不能破坏下面几条。

**两份存储，职责分开：**

| 存储 | 存什么 | 规则 |
| :--- | :--- | :--- |
| 原件库 `data/inbox/` | 每条消息的原始内容和附件原文件 | 收到即存，在任何判断之前完成；永不移动、永不修改；同一文件按内容哈希只存一份 |
| 归档 `data/archive/` | 按「日期 / 领域 / 事项」组织的浏览视图：对话记录、摘要、图片、文档、语音、视频 | 由分析结果生成；改领域、拆开、合并时跟着移动或重建；文件指向原件（硬链接），不另存副本 |

**完整：**

- 双向都存：本人发的消息、机器人的回执、提问、本人的作答、指令，都进当天的完整对话记录。
- 闲聊、与事项无关的消息、分析失败的片段、暂不支持的消息类型（红包、名片等）同样保存，分别进「其他」领域、当天完整对话记录或「未归类」。
- 附件保留原文件名和原格式。能提取文字的（PDF、Word、Excel、PPT、纯文本、语音转写、图片中的文字）另存一份提取文本，进全文检索，原件不动。

**分类：**

- 一个事项一个文件夹，放在它的主领域下。文件夹里是这个事项的对话记录、摘要，以及按种类分开的图片、文档、语音、视频。
- 附件归哪个事项，跟着它所在的消息走：切分把哪段消息分给哪个事项，那段里的附件就归哪个事项。
- 每个事项文件夹自成一体：摘要里列出全部附件的相对链接，对话记录里在附件出现的位置放链接。不打开数据库也能看懂。

**代码和模型的分工（按第 2 节）：**

| 事情 | 谁做 |
| :--- | :--- |
| 存原件、算哈希、判断文件种类（按文件头和扩展名）、去重、提取 PDF / Office 文字、生成路径、移动、建链接 | 代码 |
| 图片里是什么、文档讲的是哪件事、附件属于哪个事项、事项标题 | 模型 |
| 存档路径和文件名合法、链接都指向存在的原件、每条消息都出现在当天完整对话记录里 | 代码核验 |

**一处存放，多种清单：** 文件在归档里只放一处（日期 / 领域 / 事项）。项目清单、产品清单、文件夹结构清单和每个对象的页面都是指向同一批事项、待办和附件的链接视图，不复制文件。对象（项目、产品）有字段、状态、上下级和相互关联，新对象、状态变化、关联由模型提出、本人确认；统计字段和清单文件由代码生成。详见 [09-对象清单.md](09-对象清单.md)。

**确认前后：** 原件和当日完整对话记录在收到时就写入，不等确认；事项文件夹、摘要、附件归类属于分析结果，在本人确认写入计划之后才生成。

**跟随纠正：** 改领域就移动事项文件夹；拆开、合并时旧文件夹改名加 `.已替换` 保留，按新结果重建；撤销时恢复原路径。本人要求删除时，原件、归档链接、提取文本、数据库记录一并删除。

### 3.7 阶段确认：每一步经本人通过才往下走

**规则：**

1. 工作流按本人能看懂的**阶段**划分。每个阶段由一个或几个节点组成，结束时产出一份可读的阶段结果。
2. 每个阶段结束后停下（LangGraph `interrupt()`），把阶段结果发给本人，等本人回复。
3. 本人的回复只有四种处理：

| 回复 | 处理 |
| :--- | :--- |
| 通过 | 进入下一阶段 |
| 修改意见（自由文本） | 先判断意见针对哪个阶段；退回那个阶段，带着意见重做；该阶段之后的结果作废，重做后重新逐个确认 |
| 全部通过 | 本阶段通过，本线程后续阶段不再停下，直接执行到写入 |
| 放弃 | 不写入分析结果；原件和当日完整对话记录已在，片段进「未归类」 |

4. 重做没有次数上限，直到本人通过或放弃。重做时模型必须看到：上一版结果、本人对这一阶段的全部意见（按时间顺序），并在输出里说明「按你的意见改了什么」。
5. 意见里给出了明确的值（「领域是项目交付」「截止 11 月 5 日」「拆成两件」），就把它变成约束，由代码核验重做结果是否满足；不满足就退回模型再改，不发给本人。
6. **一次只让本人确认一件事。** 多个线程同时到达确认点时排队，前一个确认完才发下一个。这样本人的「通过」或修改意见永远只对应当前这一条，不会串。
7. 数据写入只发生在最后一个阶段「写入计划」被通过之后。之前任何阶段放弃或进程崩溃，都不会留下半截数据。
8. 每个阶段是否需要确认可在配置里单独关闭，默认全部开启。关闭的阶段直接进入下一阶段，结果仍写进最终的写入计划供确认。
9. 确认消息里的修改意见同时记一条纠正记录（第 4 节第 2 层），同类意见累计后可以提议成规则。

**确认消息的写法：** 由代码按模板生成，不让模型写。第一行写「确认 #编号 · 第几步 / 共几步 · 阶段名」，正文是阶段结果，模型拿不准的地方标「（拿不准）」并附理由，最后一行写可回复的选项。

### 3.8 用好历史：每次都查，先粗后细，关系先定

全部历史（对话、附件、条目、待办、对象）都留着，目的是让每次判断和回答都能用上。规则：

1. **不判断「要不要查历史」。** 这本身是语义判断，代码不能用「提到了名字才查」这类规则决定。每个事项、每个提问都先由代码召回一份历史目录；要不要往深处看、看哪条，由模型用只读工具自己决定。
2. **先粗后细。** 历史分层存放：清单与对象页 → 条目摘要 → 片段原文 → 附件全文。召回只给前两层，原文和附件由模型按编号、按页取。工具返回有条数和字数上限，超出就分页。
3. **新旧关系在写入时定，不在回答时临场判断。** 新内容和旧记录是重复、补充、修订、演进还是矛盾，由模型在历史判断节点给出，本人在确认时通过；代码据此保留旧值、标记取代、挂上时间线。回答时默认用最新有效的说法，并能顺着修订链讲出变化。
4. **矛盾不自动裁决。** 新旧说法冲突又看不出谁对时，列出双方原文交本人决定；没决定的标「未定」，回答时必须提到。
5. **结论必须带出处。** 每个基于历史的说法附条目编号、消息序号或附件页码，由代码核验这些引用出现在本次召回或工具结果里。
6. **长内容交给阅读工具。** 需要通读长附件或多段原文时，调用阅读工具：内部是一次只读的模型步，带着具体问题去读，只交回结论和引用位置。它是工具，不是另一个自主规划的 agent。
7. **上下文按「看得清」来控制。** 每个区块、每个节点有输入上限；循环里早先的工具结果超过上限时压成一行提要加编号，需要时可以重取。目的是让模型看得清楚，不是为了省钱。

细节见 [10-历史检索与上下文.md](10-历史检索与上下文.md)。

## 4. 纠错与修复：到底改的是什么

「自纠正」「自动修复」在本项目里分四层，每层改的东西不同。设计时必须说清楚某个机制属于哪一层。

| 层 | 触发 | 改什么 | 不改什么 | 谁做 | 何时生效 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 1. 运行内重试 | 核验不通过 | 只改**本次模型的输出**：把错误原话作为一条消息追加进对话，模型重新提交 | 代码、提示词文件、工作流、数据库都不改 | 运行时自动 | 本次模型节点内 |
| 2. 本人纠正 | 写入前：本人在阶段确认时提修改意见。写入后：本人发「改成 X」「拆开」「并到上一段」等 | 写入前：按意见重做该阶段，改的是这次的分析结果。写入后：改**数据**：条目、待办、标签、别名。两种都写一条纠正记录 | 代码、提示词文件、工作流不改 | 本人发起，代码执行 | 立即 |
| 3. 规则记忆 | 同类纠正出现 2 次，系统提议「以后都这样处理吗」，本人确认；或本人直接发「规则：……」 | 改**数据库里的规则表**：新增一行自然语言规则。下次组装上下文时自动注入 | 提示词文件、代码、工作流不改 | 本人确认后系统写入 | 下一次相关的判断 |
| 4. 离线修复 | 分错的案例进入回归样例集，开发者诊断 | 按原因改**提示词文件、核验代码、上下文组装或工具、工作流步骤**之一，出新版本 | — | 开发者（人或开发用 agent），不是线上系统 | 回归评测不退步后切换版本 |

**线上系统永远不自动修改代码、提示词文件或工作流。** 线上能自动改的只有第 1 层的本次输出；第 2、3 层改的是数据，并且都由本人发起或确认。模型自己总结的「经验」不写入任何地方。

第 4 层诊断时，按错误原因决定改哪一层，不要什么都去改提示词：

| 现象 | 原因 | 改哪里 |
| :--- | :--- | :--- |
| 输出字段缺失、取值不在代码表、编造数字，但核验没拦住 | 核验有漏洞 | 核验代码：加一条检查 |
| 本人的偏好（某客户归某领域） | 个人规则，不是通用知识 | 规则表（第 3 层），不改提示词 |
| 模型对某个定义理解错（「归最终负责交付的那一块」） | 定义写得不清楚 | 提示词文件：改定义或加示例 |
| 模型判断需要的信息不在上下文里（没看到两周前那次） | 召回不到 | 上下文组装或工具：改检索条件 |
| 该问的时候没问、该查的时候没查 | 步骤顺序或停止条件不对 | 工作流：调整步骤或模型步契约 |
| 某类任务在给定信息下模型就是判断不稳 | 任务太大或太含糊 | 工作流：拆成更小的模型步，或改成进待确认由本人决定 |

## 5. 框架选型的判断依据

选框架之前先回答：**本项目要框架替我们做什么。** 需要两层：

**流程层。** 一段内容要依次经过意图、切分、历史判断、分类、抽取几个判断，中间有分支（新事 / 补充 / 修订 / 重复 / 完成），还要在拿不准时停下来问本人，可能隔几小时后在原位继续。要求：

1. 步骤和分支能清楚地表达和修改；
2. 每一步之后自动保存状态，崩溃重启后从断点继续，已完成的模型调用不重做；
3. 能在任意一步暂停、等外部输入、再从原位继续。

**判断层。** 每个模型节点内部是一次判断。要求：

4. 输出能声明成 Pydantic 类型，框架负责校验；
5. 核验失败时能把错误原因发回模型重做（第 4 节第 1 层）；
6. 只读工具从函数签名生成，工具和结构化输出能在同一次判断里共存；
7. 能接百炼的 OpenAI 兼容接口，能控制思考模式。

| 候选 | 擅长什么 | 对本项目的结论 |
| :--- | :--- | :--- |
| LangGraph | 图、检查点、`interrupt()` 中断与 `Command(resume=...)` 恢复、子图 | 第 1–3 条原生满足，**流程层选它** |
| Pydantic AI | 带类型输出的 Agent；输出核验器抛 `ModelRetry` 自动回灌；工具从类型注解生成；OpenAI 兼容接入 | 第 4–7 条原生满足，**判断层选它** |
| LangChain 的模型与 Agent 封装 | 与 LangGraph 同一生态 | 结构化输出和核验回灌不如 Pydantic AI 直接；节点里不用，避免两套模型调用写法 |
| Pydantic AI 自带的 `pydantic-graph` | 也能做图和状态持久化，依赖轻 | 暂停等人、原位继续的支持和实践不如 LangGraph 成熟 |
| OpenAI Agents SDK | 多 agent 交接、OpenAI 托管工具 | 以 OpenAI 模型和接口为先；本项目不需要多 agent |
| 自己写流程和循环 | 零依赖 | 第 2、3、5 条都要自己写，正是最容易出错的部分 |

约束：

- 两个框架各守一层。图的代码只调用判断函数（输入上下文，返回 Pydantic 对象），不直接引用 Pydantic AI 的类；判断函数不知道自己在哪张图里。换掉其中一个只改一层。
- 业务数据只由图里的代码节点写入，检查点只记录流程。两边不一致时以业务库为准，写入以线程编号为幂等键。
- 版本钉死，升级走回归评测。

## 6. 设计稿必须回答的问题

提交任何新的或修改过的工作流设计，逐条回答：

1. 触发条件是什么？是代码精确匹配，还是模型判断意图？
2. 每一步是代码步、模型步还是工具步？对每个代码步，用第 2.2 节的「换个说法测试」检查它有没有偷偷做语义判断。
3. 每个模型步的五项契约（第 3.2 节）是什么？
4. 模型判断需要的历史和实体信息从哪里召回？召回不到会怎样？模型能用哪些工具往深处查？新旧不一致、重复、修订时怎么处理（第 3.8 节）？
5. 循环的三个停止条件是什么？停在失败上时，原文和本人能看到什么？
6. 本人怎么纠正这条工作流的结果？纠正改的是哪一层（第 4 节）？会不会进规则记忆？
7. 哪些错误能被代码核验发现？发现不了的靠什么兜底（待确认、本人纠正）？
8. 这条工作流分几个阶段确认？每个阶段发给本人的结果长什么样？本人提意见时退回到哪个节点重做？哪些意见能变成代码可核验的约束？
9. 这条工作流新建、移动或改名了哪些存档文件？失败、纠正、撤销之后，原件和归档是否仍然完整、一致（第 3.6 节）？
10. 有哪些回归样例覆盖这条工作流？

## 7. 用词

文档和对话里统一用下面的说法，不要混用：

| 说法 | 指什么 |
| :--- | :--- |
| 运行时 | 包住模型的那一层代码，即 harness：LangGraph 的图加上图里的代码节点 |
| 线程 | 一张图的一次执行，例如一个片段的处理，状态由检查点保存 |
| 模型节点 | 图里的一个判断步骤，内部是一个 Pydantic AI Agent |
| 阶段 | 本人确认的单位，由一个或几个节点组成（第 3.7 节） |
| 确认 | 阶段结束时停下等本人「通过」或提意见 |
| 模型步 | 一次模型调用 |
| 核验 | 模型输出之后、执行动作之前的代码检查 |
| 重试 | 第 4 节第 1 层，只在一个模型节点内 |
| 纠正 | 第 4 节第 2 层，本人发起 |
| 规则 | 第 4 节第 3 层，本人确认过的规则表条目 |
| 修复 | 第 4 节第 4 层，开发者离线做 |
