# 邮件改为工作日按小时汇总

日期：2026-11-24  
状态：待审阅（审阅通过后再写实现计划）  
范围：`wechat_AI_assistant` 的邮件拉取、微信推送、全景图与对应说明

## 目标

白名单邮件不再全天每 2 分钟拉取，也不再每封信立刻走一遍分拣并推微信。工作日在固定时点汇总：有新邮件才推一条；夜里和周末不拉取、不调用模型、不推送。21:00 之后到达的邮件（含欧洲下午来信）留到下一个工作日 08:30 一次给出。

## 时间

与现有早晚报相同，使用服务器本地时间。部署机时区为东八区（`Asia/Shanghai`）。只在周一到周五运行，规则与现有简报一致（`weekday < 5`）。法定假日若落在周一到周五，照常运行，不另做节假日日历。

| 时点 | 行为 |
| :--- | :--- |
| 08:30 | 拉上次成功水位之后的全部积压（周二至周五含前一晚 21:00 之后；周一含周五 21:00 至周一 08:30，即含周末）。有白名单邮件则另发一条微信。早报照旧、单独发送。 |
| 09:00、10:00、11:00、12:00、13:00、14:00、15:00、16:00、17:00、18:00、19:00、20:00、21:00 | 只处理该时点相对上次水位的新邮件。有则推一条，没有则不发。18:00 晚间复盘照旧、单独发送。 |
| 21:00 这一班完成之后，到下一次工作日 08:30 | 不访问邮箱，不调用模型，不推微信。 |

不设 08:00 班，避免与 08:30 连发两条。某一小时没有任何白名单邮件时，不发送「本小时无邮件」。

调度方式：后台约每 30 秒看一次时钟（与简报同一风格）。某个时点从到达起 5 分钟内若还没成功跑完，就允许开始一次。同一时点同时只跑一批：上一批还在调用模型时，不再开第二批。成功后当天该时点不再跑。5 分钟窗口内开始的一批可以在窗口结束后跑完；若它失败，或 5 分钟内根本没能成功，则放弃这一班，水位不前移，下一班会把这批信一起带走。

## 微信上的「验签解密 / 已收到」和邮件无关

全景图阶段一的「接入与预处理」把微信和邮件写在同一格，这两句只描述微信：

- **验签**：你发到个人微信的内容先到腾讯。腾讯推送到我们的回调地址时，附带用 Token、时间戳、随机串和密文算出来的签名。服务用同一套 Token 再算一遍，签名一致才收下。不一致就丢掉，避免别人伪造或改过的请求进入系统。
- **解密**：正文是 AES 加密的。验签通过后，用企业微信后台的 EncodingAESKey 解开，才能看到文字、语音或文件。
- **0.5 秒内回「已收到」**：只回给你本人，表示这条微信已经进系统。后面的分析还要几秒，所以先回一句，避免你以为没送到。现有文案按类型区分，例如「已收到，正在为您分析处理」「已收到语音，正在转写并分析」「已收到附件，正在解析并分析」。

邮件由服务主动向微软 Graph 读取，没有腾讯这道签名，也没有人在等一句到达回执。邮件 **不** 发送「已收到」。你在微信里看到的唯一一句，就是到汇总时点才发的「邮件汇总」：收件是确认卡，发件列在同一条里。

全景图这一格改成两段：上面保留微信的验签、解密和「已收到」；下面写邮件不回「已收到」、到点才发汇总、域名以配置文件为准。

## 域名名单

处理哪些邮件由 `config/mail_domains.json` 决定，不再使用环境变量里的 `V&F,Tera,B&D` 名称片段，也不再在主题或正文里搜公司名。用 JSON 而不是 XML：项目里已经用 JSON，加一个域名就是改一行，不需要额外的解析库。

```json
{
  "domains": [
    "palmarytech.com",
    "wissentek.com",
    "budi.de",
    "vandf.com",
    "tera-instruments.com"
  ]
}
```

每个汇总时点开始时重新读这个文件。改完保存即可，不用重启，下一班生效。文件缺失或 JSON 不合法时，本班不拉取、不前移水位，并记下错误；若进程里还有上一班成功读到的名单，本班继续用那一份。名单为空时，不处理任何邮件。

一封信要处理，须同时满足：

- 发件人、收件人或抄送中，至少有一个地址的域名等于名单中的域名，或是其子域名（`sales.vandf.com` 算 `vandf.com`）。
- 这个地址不是邮箱自己（`MAIL_USER`，当前默认 `info@wissentek.com`）。只有邮箱自己的地址命中时不算，避免「邮箱在 wissentek.com 上，于是每封信都命中」。

因此：对方是这五个域名之一的来信和你发给他们的信会处理；广告、验证码以及名单以外的客户来信不处理。同事地址若是 `@wissentek.com` 或 `@palmarytech.com`，也算命中，会按收件做成确认卡。退订、验证码、`unsubscribe`、`noreply`、`no-reply` 即使域名命中也跳过。

## 收件与发件

域名规则见上一节。退订、验证码、`unsubscribe`、`noreply`、`no-reply` 仍直接跳过。

邮箱按文件夹增量读取，不再用「整个邮箱最近 15 封」：

- 收件箱：`mailFolders/inbox/messages`，按 `receivedDateTime` 过滤并排序。
- 已发送：`mailFolders/sentitems/messages`，按 `sentDateTime` 过滤并排序。
- 每页 50 封，沿 `@odata.nextLink` 取完本时段窗口。草稿箱和已删除不读。

### 收件

同一时点里命中的收件合成 **一次** 分拣（一次 `handle_incoming_turn`，`thread_id` 仍为 `owner`），出 **一张** 确认卡。这一次指定走工作交办（路径④），不把整批邮件交给路由模型去判成闲聊或查档。一张卡里可以有多条拟入库动作。回复方式不变：`1` 确认落盘，`2` 仅存想法，`改：` 调整。

并成一张卡的原因：保存新确认卡时会把同一对话里上一张待确认卡标成被取代，而 `1` 只确认最新一张。同一小时若拆成多张卡，前面的卡无法再确认。

单次最多分析 10 封收件（按时间从旧到新）。超出的留在邮箱水位之后，下一班再分析。

### 发件

你发出的、且对方域名在名单里的信 **不** 进入起草模型， **不** 建确认卡。它们写进同一条微信：时间、对方地址、主题。

主题或正文摘要（忽略大小写）出现下列任一内容时，该行末尾加上「可能在等对方」：

`?`、`？`、`请回复`、`请确认`、`盼复`、`please confirm`、`please advise`、`kindly advise`

这是确定性标记，允许把带问号的主题误标成「可能在等对方」，不用模型纠正。

分拣收件时，提示词里附上这些已发送的一行摘要，并写明：已发送只用来判断收件是否已经回复，不要为已发送邮件新建待办。已发送正文不整段送入模型。已发送内容仍包在 `[UNTRUSTED_EXTERNAL_DATA]` 内。

单次最多记 10 封已发送，按时间从旧到新。超出的下一班再记。

### 已有未确认卡

调用分拣之前，在引擎的 turn 锁内读取 `owner` 的最新待确认卡，避免微信消息刚好在检查和分拣之间插入一张新卡。

- 有待确认卡，且本班有新的收件：不调用分拣，不把这些收件标成已处理，收件水位不前移。微信发一条说明：列出收件主题，写明确认卡编号还在，回复 `1`、`2` 或 `改：` 之后，下一班再分析这些收件。本班的已发送仍写在这条里，并标成已处理、前移已发送水位。
- 有待确认卡，但只有已发送、没有新收件：只推已发送列表，不提确认卡，不调用分拣。
- 没有待确认卡：按上面的收件规则分拣。

## 水位与去重

新表 `mail_poll_cursor`：`folder`（`inbox` 或 `sent`）为主键，`watermark_utc` 为该文件夹已完成处理的时间（UTC，ISO-8601）。

去重仍用 `seen_external_ids`（`internetMessageId`，没有则用 Graph `id`）。只有这条消息已经真正处理完，才写入 seen：

- 收件：已纳入一次成功推送的分拣，或属于噪音 / 非白名单被跳过。
- 发件：已写入一条成功推送的汇总，或属于噪音 / 非白名单被跳过。
- 因已有确认卡而推迟的收件：不写入 seen。

查询使用「水位减 2 分钟」作为重叠，避免时钟偏差漏信；重叠区内已 seen 的信直接跳过。

水位前移：

- 本班该文件夹的白名单邮件全部处理完（含「没有新邮件」）：水位设为本班开始时间。
- 因 10 封上限或未确认卡而留下收件：收件水位停在最旧一封未处理收件的 `receivedDateTime` 减 2 分钟。
- 推送或分拣失败：对应文件夹水位不前移，本班写入的确认卡要取消（只取消本班新建的那张），相关邮件不写入 seen。下一班整批重试。

第一次没有水位时，不回拉历史全库：

- 跑到的是 08:30：水位种子为上一个工作日 21:00（周一即上周五 21:00）。
- 跑到的是 09:00–21:00：水位种子为当天 08:30。

服务在白天中途重启时，已 seen 的信不会再次出卡；水位还没前移的信会在下一个时点重做。

## 微信一条长什么样

有白名单邮件才发。邮件汇总与 08:30 早报、18:00 晚间复盘是不同的消息。邮件这条不走 12 秒进度心跳，避免一小时内先刷出多条「正在处理」。

有确认卡时：

```text
📧 邮件汇总（11:00）

📋 确认 #104｜……
（现有确认卡全文，含回复 1 / 2 / 改：）

你发出 1 封（不建卡）：
- 10:40 发给 support@tera-instruments.com｜Re: Spectrometer delivery｜可能在等对方
```

距上次水位超过 70 分钟（夜间或周末积压）时，标题为 `📧 邮件汇总（08:30，含此前未推送的邮件）`。

只有已发送时，不出现确认卡，也不写「没有收件」，直接列出「你发出 N 封（不建卡）」。

因未确认卡而推迟时：

```text
📧 邮件汇总（11:00）
这小时有 2 封收件：V&F 报价更新；Tera 交期。
确认卡 #88 还没回复，本班不生成新卡。回复 1、2 或「改：…」之后，下一班再分析这些收件。

你发出 1 封（不建卡）：
- 10:40 发给 support@tera-instruments.com｜Re: Spectrometer delivery
```

分拣跑完但没有产生确认卡（例如只要澄清）：仍推这一条，正文用模型的回复，并附上已发送列表（若有）。

确认卡全文始终整段保留，不截断卡片正文（与现在单卡推送一样，卡片本身有多长就发多长）。确认卡之外的已发送列表若会让整条超过 1800 个字符，从最旧开始保留，末尾写「另有 N 封已发送未列出」；仍然放不下时，已发送列表改成这一句计数。

## 测试

- 周二 11:00 会跑，周二 22:00 与周六任意时间不跑。
- 周一 08:30 的首次水位是上周五 21:00；周三 15:00 首次水位是当天 08:30。
- 同一时点 2 封收件只调用一次分拣，不经过路由模型，直接走工作交办，只产生一张待确认卡。
- `sales@vandf.com` 发给邮箱的信要处理；`news@randomvendor.com` 发给邮箱的信不处理；只有邮箱自己的地址落在 `wissentek.com` 上时也不处理。
- `colleague@wissentek.com` 的来信要处理。
- 发给 `support@tera-instruments.com` 的已发送邮件不调用分拣，出现在汇总里；带「请确认」的标成「可能在等对方」。
- 每个时点重新读取 `config/mail_domains.json`；文件损坏时不前移水位。
- 已有待确认卡时，新收件不调用分拣、不写入 seen、收件水位不前移；已发送仍进入这条微信并写入 seen。
- 推送失败时取消本班新建的确认卡，水位不前移，同一封信下一班还会出现。
- 域名不在名单里的邮件，以及退订邮件，不进微信，但写入 seen，不挡住水位。
- 第 11 封收件留到下一班。
- 已见过的 `internetMessageId` 不再次分拣。
