系统保存了全部对话、图片、文档和分析结果。本文回答三个问题：

1. 处理一段新内容或回答一个提问时，怎么决定只看当前内容，还是去查历史（第 1、3 节）；
2. 历史可能很大，怎么既用上又控制上下文（第 2、5 节）；
3. 新内容和历史重复、补充、修订、演进或矛盾时，各怎么处理（第 4 节）。

做法参考了 Cursor、Claude Code 这类编码智能体：它们不把整个代码库塞进上下文，而是给模型一份目录和一组搜索、打开文件的工具，由模型自己决定看什么、看多深。对照见第 7 节。

## 1. 原则

| 原则 | 含义 |
| :--- | :--- |
| 每次都召回 | 「这句话要不要查历史」是语义判断，代码不做。每个事项、每个提问都由代码先召回一份历史目录 |
| 深读由模型决定 | 目录不够时，模型用只读工具按编号、按页往下取；够了就停 |
| 先粗后细 | 召回只给清单、对象页和条目摘要，原文和附件全文按需取 |
| 关系写入时定 | 新旧关系由 judge 判定、本人在阶段 2 确认，写进关联表；回答时直接用，不临场再判 |
| 矛盾交本人 | 看不出谁对的冲突不自动选，标「未定」，直到本人裁决 |
| 结论带出处 | 每个基于历史的说法附编号、消息序号或页码，代码核验引用真实存在 |
| 看得清优先 | 上下文上限是为了让模型看清，不是为了省钱；需要的信息不因为长而不给，而是分层、分页、提要 |

## 2. 历史的分层

| 层 | 内容 | 由谁生成 | 典型大小 | 怎么拿到 |
| :--- | :--- | :--- | :--- | :--- |
| 0 目录层 | 项目清单、产品清单、对象页摘要（[09](09-对象清单.md)）；客户、供应商、人员的实体卡片 | 代码，每次写入后更新 | 每个对象几百字 | 召回直接给；`get_object`、`list_objects` |
| 1 摘要层 | 每个条目的摘要卡：编号、日期、领域、标题、摘要、决定、待办、关联对象、新旧关系、是否有效 | 片段处理图写入时生成 | 每条一两百字 | 召回直接给；`search_records`、`get_item` |
| 2 原文层 | 片段的完整对话，按消息序号 | 原件库 | 几千字 | `get_segment`，可指定消息范围 |
| 3 附件层 | PDF、Office、语音转写、图片描述的提取文本，按页或按段 | 代码提取；图片描述由看图节点生成（第三期） | 可能几万字 | `get_attachment_text`，按页；或交给 `read_long` |

摘要卡是让历史可用的关键：它短、结构固定、带编号，模型扫几十条也看得清，需要细节再按编号下钻。

## 3. 召回与展开

### 3.1 代码召回：每次都做

片段处理图的 recall 节点按 [05](05-片段处理图.md) 第 4.4 节召回标签、历史条目、未完成待办、项目和产品。问答图在 answer 节点开始前做同样的召回：按问题里的名字、对象和全文检索，给出第 0、1 层的候选。

召回宁多勿漏。召回的东西相不相关由模型判断，代码不用相似度阈值替模型下结论（00 第 2.4 节）。

### 3.2 模型展开：只读工具

| 工具 | 层 | 参数 | 返回 | 单次上限 |
| :--- | :--- | :--- | :--- | :--- |
| `lookup_entities` | 0 | 名字 | 匹配的标签和对象，附别名 | 10 个 |
| `get_object` | 0 | 对象编号 | 对象页摘要、上下级、关联、最近记录 | 1 个 |
| `list_objects` | 0 | 类型、状态、客户 | 对象列表 | 30 个，可翻页 |
| `related_objects` | 0 | 对象编号、关系 | 顺着关联查到的对象 | 20 个 |
| `search_records` | 1 | 关键词、时间范围、领域、对象、页码 | 摘要卡列表 | 每页 10 条 |
| `get_item` | 1 | 条目编号 | 完整摘要卡和附件清单 | 1 条 |
| `get_history_chain` | 1 | 条目编号 | 这件事的时间线：补充、修订、演进、矛盾各条，标明哪些已被取代 | 30 条 |
| `list_todos` | 1 | 状态、对象、负责人 | 待办列表 | 20 条 |
| `get_segment` | 2 | 片段编号、消息序号范围 | 原文 | 4000 字，超出提示还有多少 |
| `get_attachment_text` | 3 | 附件编号、页码 | 一页或一段提取文本 | 4000 字，可翻页 |
| `read_long` | 2、3 | 附件或片段编号列表、具体问题 | 结论和引用位置（消息序号、页码） | 结论 800 字 |

全部只读。返回内容一律带编号；超出上限时截断并写明「第 1 / 5 页，共约 18000 字」，模型可以继续翻页。

`read_long` 是阅读工具：内部是一次单独的模型步（Pydantic AI 判断函数），带着具体问题读长文，只交回结论和引用位置。主流程的上下文里只出现这份结论，长文本身不进去。它的结论也要过核验：引用的页码和消息序号必须存在，结论里的数字必须出现在原文里。

### 3.3 每个节点能用什么

| 节点 | 召回给什么 | 可用工具 | 工具调用上限 |
| :--- | :--- | :--- | :--- |
| judge | 第 0、1 层候选 | `lookup_entities`、`get_object`、`search_records`、`get_item`、`get_history_chain`、`get_segment`、`get_attachment_text` | 8 次 |
| classify | 阶段 2 确认过的对象和条目摘要 | 无 | — |
| extract | 候选待办、阶段 2 确认过的关系及有关系的条目摘要卡、对象当前字段 | 无 | — |
| reconcile | 旧待办 | 无 | — |
| answer | 第 0、1 层候选 | 第 3.2 节全部 | 15 次（`read_long` 算一次） |

classify、extract 不开工具：它们需要的历史在阶段 2 已经由 judge 找齐并经本人确认，直接作为上下文给出。

### 3.4 停止

按 00 第 3.4 节：每轮要么调工具、要么提交结果。达到工具调用上限时，模型必须用已有信息提交，并在输出里写明查过的范围（时间段、来源）和没查到的部分。这条范围说明在回答或确认消息里原样展示给本人。

## 4. 新旧关系

### 4.1 关系种类

judge 对每个事项判断它和历史条目的关系。原来的 `continues` 拆成补充和演进，并新增修订和矛盾：

| 关系 | 代码 | 含义 | 例子 |
| :--- | :--- | :--- | :--- |
| 新事 | `new` | 和已有记录无关 | 第一次提到的询价 |
| 重复 | `restates` | 同一件事又说了一遍，没有新信息 | 同一份方案转发了两次 |
| 补充 | `supplements` | 同一件事加了新信息，旧信息仍有效 | 报价之后补了运费 |
| 修订 | `revises` | 新说法取代旧说法的某些内容 | 交期从 11 月 5 日改到 6 日 |
| 演进 | `advances` | 同一件事进入下一阶段 | 报价谈成，进入合同 |
| 矛盾 | `conflicts` | 新旧说法冲突，看不出哪个对 | 采购说要 500 台，销售说 300 台 |

一个事项可以和多条历史条目有关系，每条单独给出。

### 4.2 判定与核验

judge 对每条非 `new` 的关系给出：

| 字段 | 内容 |
| :--- | :--- |
| `item_id` | 历史条目编号 |
| `relation` | 上表之一 |
| `changed_facts[]` | 修订和矛盾必填：哪一项（如交期、数量、价格、负责人、对象状态）、旧说法原文、旧说法所在的条目和消息、新说法原文、新说法所在的消息 |
| `reason` | 一两句理由 |

代码核验：

- `item_id` 必须来自召回或本次工具结果；
- `revises`、`conflicts` 必须有 `changed_facts`；
- 旧说法原文必须是那条历史条目原文或摘要卡的子串，新说法原文必须是本次事项原文的子串；
- 同一项不能既被判为修订又被判为矛盾。

判断两种说法「是不是在讲同一项」「算修订还是矛盾」是语义判断，由模型做；代码只核验引用。

### 4.3 写入后的效果

| 关系 | 条目 | 待办 | 对象 | 存档 |
| :--- | :--- | :--- | :--- | :--- |
| 重复 | 不新建条目，只在旧条目上加一个来源 | 不新建 | 不变 | 片段原文照存，归入旧事项文件夹的「后续」 |
| 补充 | 新建条目，关联到旧条目 | 按 extract 结果 | 按 extract 结果 | 新事项文件夹，摘要里链接旧事项 |
| 修订 | 新建条目，关联到旧条目；旧条目被修订的那一项标「已被 #新编号 取代」 | 涉及的待办字段按新值更新，旧值进字段历史 | 涉及的字段按新值更新，旧值进 `object_history` | 同上；旧事项摘要追加一行「某项已于某日修订，见…」 |
| 演进 | 同补充，关联类型为演进 | 旧阶段的待办可能被 extract 标完成 | 状态变化按 extract 结果 | 同补充 |
| 矛盾 | 新建条目，关联类型为矛盾，状态「未定」 | 涉及的待办字段不改，标「有冲突」 | 涉及的字段不改，标「有冲突」 | 同补充；两边摘要都写「与 #编号 有冲突，未定」 |

旧值永不删除，只标失效时间和取代来源，所以随时能回答「原来是多少、哪天改的、谁说的」。

### 4.4 在确认里怎么呈现

阶段 2（关联）的确认消息逐条列出关系。修订和矛盾附双方原文：

```text
第 1 件 某科技二期方案
  · 修订 #231（10 月 28 日）：交期「11 月 5 日」→「11 月 6 日」
  · 矛盾 #240（10 月 30 日）：数量 采购「500 台」／ 销售「300 台」
      回复「改：以新为准」「改：以旧为准」或「改：都保留」；不说明就记为未定
```

本人对矛盾的裁决处理：

| 裁决 | 处理 |
| :--- | :--- |
| 以新为准 | 改为修订 |
| 以旧为准 | 新说法记为「未采纳」，旧值不变 |
| 都保留 / 未说明 | 保持未定，每日清单里列出，直到本人裁决（「定 #240 300 台」或在对话中说明） |

写入之后发现的矛盾和修订，走纠正图（[06](06-纠正查询与清单.md) 第 1 节），改动类型「改关系」「裁决冲突」。

### 4.5 回答时怎么用

- 默认用最新有效的说法作答。
- 用到的记录有「未定」冲突时，必须在回答里写出双方说法，代码核验：引用的条目中有未定冲突而回答的 `conflicts` 为空，就退回模型重写。
- 问题问的是变化（「交期改过几次」「方案是怎么演变的」），用 `get_history_chain` 按时间线回答。
- 对比类问题（「两版报价差在哪」）不是存储的关系，由 answer 在回答时用 `read_long` 或两次 `get_attachment_text` 读出两边再比，结论带两边的引用。

## 5. 上下文的大小

### 5.1 上限

| 位置 | 默认上限 | 超出时 |
| :--- | :--- | :--- |
| 召回的各区块 | 见 [05](05-片段处理图.md) 第 4.4 节 | 按时间从近到远截取，并告诉模型「还有 N 条，可用工具查」 |
| 单次工具返回 | 4000 字或第 3.2 节的条数 | 分页 |
| judge 的整个输入 | 3 万字 | 先压缩最早的工具结果，再压缩候选历史的摘要卡为一行标题 |
| answer 循环内的累计输入 | 6 万字 | 同上 |

数字都在配置里，可调。上限按「模型看得清」来定，以评测结果为准调整，不按费用定。

### 5.2 压缩

循环里早先的工具结果超过上限时，用一行提要替换：「第 3 次查询 search_records(某科技, 近 90 天)：10 条，编号 #201–#240，最相关 #231、#240」。编号保留，模型需要时可以重取原内容。实现上用 Pydantic AI 的消息历史处理函数，在每次调用模型前由代码执行，不用模型做压缩。

### 5.3 长片段和长附件

长片段按 [07](07-上下文提示词与核验.md) 第 1.4 节切块提要。长附件不整篇放进任何节点的上下文：判断时用 `read_long` 针对具体问题读，存档和全文检索仍用全文。

## 6. 问答图的检索流程

[06](06-纠正查询与清单.md) 第 2 节的 answer 节点按下面的方式工作，图的形状不变。

1. **召回**：代码按问题召回第 0、1 层候选，连同今天的日期、本人规则一起给模型。
2. **展开**：模型自己决定查什么。常见路径：
   - 现状类（「某某二期到哪一步了」）：`get_object` → 最近几条摘要卡 → 未完成待办；
   - 变化类（「交期改过几次」）：`get_history_chain`；
   - 汇总类（「这个月有哪些没回的报价」）：`search_records` 带时间和类型筛选，翻页直到查完；
   - 细节类（「合同里付款条件怎么写的」）：`get_item` 找到附件 → `read_long`；
   - 对比类：两边各读一次再比较。
3. **提交**：

| 字段 | 内容 |
| :--- | :--- |
| `answer` | 回答正文 |
| `cited[]` | 引用的条目、待办、对象编号，附消息序号或页码 |
| `scope` | 查过的范围：时间段、对象、来源种类 |
| `conflicts[]` | 用到的未定冲突，双方说法 |
| `not_found` | 是否没查到 |

4. **核验**：`cited` 都出现在本次工具结果里；回答里的数字都出现在工具结果里；有未定冲突就必须写进 `conflicts`；`not_found` 为真时回答不能编造。
5. **发送**：正文不超过 500 字直接发；需要更长的整理（汇总表、对比）写成 `data/archive/问答/<日期>/<时分-问题>.md`，发三行要点并附文件。企业微信机器人能否发文件在第一期实测；不能就分多条发送。

## 7. 和编码智能体的对照

| Cursor、Claude Code 的能力 | 本系统的对应 |
| :--- | :--- |
| 代码库目录、repo map | 项目清单、产品清单、对象页（第 0 层） |
| 全文搜索、语义搜索 | `search_records`、`lookup_entities`，FTS5 全文检索 |
| 打开文件、读指定行 | `get_segment`（按消息序号）、`get_attachment_text`（按页） |
| 子智能体读大量文件 | `read_long` |
| 长对话自动压缩 | 第 5.2 节压缩 |
| 项目规则文件（`AGENTS.md`、rules） | 本人规则（[07](07-上下文提示词与核验.md) 第 1.1 节） |
| 改代码前给出 diff 让人审 | 阶段确认，最后确认写入计划 |
| 检查点、撤销 | LangGraph 检查点、变更记录、「撤销」 |
| git 历史、blame | 字段历史、`get_history_chain` |

能力的来源有四块：模型本身、工具设计、上下文管理、评测与打磨。LangGraph 和 Pydantic AI 负责后三块的骨架。本系统的数据结构是自己设计的（有摘要卡、编号、清单），比编码智能体面对的陌生代码库更规整，所以在「查本人的工作历史并综合分析」这件事上，可以做到同一级别。需要持续投入的是工具的颗粒度和返回格式，以及第 8 节的评测集。

和编码智能体的一点不同要保留：编码智能体可以自主规划多步并直接改文件；本系统的自由探索只发生在 judge 和 answer 内部，且只读，写入始终走固定阶段并经本人确认（00 第 3.7 节）。

## 8. 评测

加入 [08](08-选型与实施.md) 的回归集：

| 样例 | 期望 |
| :--- | :--- |
| 交期改过一次后问「交期是哪天」 | 答新值，提到原来是旧值、哪天改的 |
| 采购和销售说的数量不一致 | 阶段 2 列为矛盾附双方原文；未裁决时问答必须提到冲突 |
| 同一份方案转发两次 | 第二次判为重复，不新建条目和待办 |
| 报价之后补运费 | 判为补充，问答时两部分合并作答 |
| 报价谈成签合同 | 判为演进，项目状态变化在阶段 4 列出 |
| 答案在附件第 7 页 | answer 用 `read_long` 或翻页找到，引用页码 |
| 跨三个月的「这个项目怎么演变的」 | 按时间线回答，每个节点带编号 |
| 问一件从没记录过的事 | `not_found` 为真，不编造 |
| 召回候选里没有、但原文明显指向一件 80 天前的旧事 | judge 用 `search_records` 找到并关联 |
| 工具调用到上限 | 提交结果并写明查过的范围 |

## 9. 数据

| 表 | 变化 |
| :--- | :--- |
| `item_links` | 关系改为 `restates` / `supplements` / `revises` / `advances` / `conflicts`；加 `changed_facts`（JSON）、状态（有效 / 未定 / 已裁决 / 未采纳）、裁决的 `reviews` 或纠正编号 |
| `field_history`（新） | 对象种类（条目 / 待办）、编号、字段、值、生效时间、失效时间、取代来源条目、依据消息、确认编号。项目和产品的字段历史仍在 `object_history`（[09](09-对象清单.md) 第 8 节），结构相同 |
| `items` | 加摘要卡所需字段的冗余列，便于召回直接取 |
| `qa_log`（新） | 问题、回答、`cited`、`scope`、工具调用记录编号；问答的完整过程仍在 `model_calls` |
