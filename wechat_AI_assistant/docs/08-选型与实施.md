## 1. 技术选型

### 1.1 语言与进程

Python 3.12，`asyncio`，单进程、单实例（[02](02-技术路线.md) 第 9 节已定）。连接器、片段器、图的执行、定时任务都在同一进程内以协程运行。

### 1.2 编排：LangGraph

| 用到的能力 | 用法 |
| :--- | :--- |
| 图 | 每张图一个 `StateGraph`，状态是 Pydantic 模型；分支用条件边 |
| 检查点 | `langgraph-checkpoint-sqlite` 的异步 SQLite 检查点，存在单独的 `data/checkpoints.db`，与业务库分开 |
| 线程 | 线程编号按 [04](04-工作流总览.md) 第 3 节，如 `seg:1024`；一个线程对应一个片段、一次纠正、一次提问或一条规则提议 |
| 中断 | 每个阶段结束的 review 节点调用 `interrupt()`；接入层收到本人回复后用 `Command(resume=...)` 恢复；修改意见经 revise 节点后沿条件边跳回对应阶段 |
| 子图 | 纠正图的 reanalyze 以子图方式复用片段处理图的 split 到 extract |
| 节点重试 | 模型节点配重试策略，只针对网络和接口错误，最多 3 次，指数退避 |
| 防死循环 | 每次执行设递归上限（初值 30） |

启动时恢复：进程启动后列出所有未结束且未处于暂停的线程，逐个从最后一个检查点继续。停在确认点的线程不动，等本人回复；已发出的确认消息不重发。

不选的方案：

| 方案 | 不选的原因 |
| :--- | :--- |
| 普通 Python 加自建 Run 表（原方案） | 暂停后原位继续、每步存档、崩溃恢复都要自己写，正好是 LangGraph 已有的 |
| Pydantic AI 自带的 `pydantic-graph` | 也能持久化状态，依赖更轻；但「流程中途停下等人、隔几小时再继续」的支持和社区实践都不如 LangGraph 成熟 |
| Temporal 一类工作流引擎 | 要另跑一个服务端，对单人单机的系统太重 |

### 1.3 模型节点：Pydantic AI

- 每个模型节点一个 Agent：输出类型是该节点的 Pydantic 模型，依赖对象里放上下文和只读查询句柄，核验写成输出核验器。
- 输出核验失败时抛 `ModelRetry`，输出重试次数设为 2。
- 有工具的节点（judge、answer）设请求次数上限：judge 8 次，answer 10 次。仅用于防死循环。
- 模型通过 OpenAI 兼容方式接百炼：指定 `base_url` 为 `https://dashscope.aliyuncs.com/compatible-mode/v1`，密钥来自环境变量；思考模式通过模型设置里的额外请求参数传入。
- 图的代码只调用每个节点的判断函数（输入上下文对象，返回 Pydantic 对象），不直接引用 Pydantic AI 的类。

### 1.4 存储

| 存储 | 内容 | 说明 |
| :--- | :--- | :--- |
| `data/app.db` | 业务数据：[02](02-技术路线.md) 第 8 节的表，加本文第 2 节的表 | SQLite，WAL 模式，FTS5 `trigram` 全文索引 |
| `data/checkpoints.db` | LangGraph 检查点 | 含正文，与业务库同等保护。已结束线程的检查点默认 30 天后删除 |
| `data/archive/` | 存档文件 | 见 [02](02-技术路线.md) 第 8.2 节 |

业务数据只由 commit、apply、save 这几个代码节点写入。检查点只记录流程走到哪、各节点的输出。两边不一致时以业务库为准：commit 以线程编号为幂等键，崩溃后重跑不会写两次。

### 1.5 追踪与日志

- 流程追踪：LangGraph 的检查点历史就是每一步的状态快照，可以按线程回放。
- 模型调用记录：每次模型调用写一行 `model_calls`：线程、节点、提示词版本、完整消息记录、输出、核验错误、重做次数、耗时。分错时看这里就知道模型当时看到了什么。
- 不接 LangSmith 或任何云端观测服务，因为追踪里有正文。
- `journalctl` 日志只有线程编号、节点名、状态、错误码，不含正文（[02](02-技术路线.md) 第 10 节）。

### 1.6 定时任务

都用进程内 `asyncio` 任务，状态在数据库：片段扫描（每 5 秒）；确认队列发送（当前没有已发送未回复的确认时，发出队首那条）；每日清单；已结束线程的检查点和模型调用记录清理（每天）。

### 1.7 依赖

`langgraph`、`langgraph-checkpoint-sqlite`、`pydantic`、`pydantic-ai-slim[openai]`、`websockets`、`httpx`、`pytest`；附件文字提取用 `pypdf`、`python-docx`、`openpyxl`、`python-pptx`，文件种类识别用 `filetype`（按文件头判断）。版本在步骤 A 时钉死，回填 [03](03-部署实施.md) 的依赖清单；升级任何一个都要跑回归。

### 1.8 代码结构

```text
wechat_agent/
  intake/       连接器、收件库与原件库、附件文字提取、固定指令与确认回复匹配、确认队列、片段器
  graphs/       四张图的定义、状态模型、交接与恢复
  judges/       每个模型节点：Agent、输出模型、核验器
  context/      召回、摘要卡、上下文组装与上限、循环内压缩、实体卡片、规则读取
  tools/        只读查询函数（给 judges 用），分页与截断；read_long 阅读工具（10 第 3.2 节）
  storage/      SQLite 访问、迁移、全文索引、变更记录
  archive/      存档器、清单与对象页生成（09 第 5 节）
  reply/        回执模板、每日清单
  prompts/      提示词包（07 第 2.1 节）
tests/
  unit/         代码节点、召回、核验器
  judges/       每个模型节点的回归样例
  graphs/       用假判断函数跑通图的分支、中断、恢复
  e2e/          片段到数据库写入的端到端样例
```

依赖方向：`graphs` 用 `judges`、`context`、`storage`、`archive`、`reply`；`judges` 只用 `tools` 和 `context` 给的数据，不写库；`intake` 只用 `graphs` 的启动和恢复入口。

## 2. 数据表增量

在 [02](02-技术路线.md) 第 8 节的表之外：

| 表 | 主要字段 | 约束 |
| :--- | :--- | :--- |
| `attachments` | 附件编号、来源 `msgid`、种类（图片 / 文档 / 语音 / 视频 / 其他）、原文件名、大小、内容哈希、原件路径、提取文本路径、提取状态 | 内容哈希唯一：同一文件只存一份原件，多条消息指向它 |
| `threads` | 线程编号、图名、处理对象、状态（运行中 / 暂停 / 已完成 / 已降级）、创建和更新时间 | 线程编号唯一。供恢复、清单、排查用 |
| `reviews` | 确认编号、线程编号、阶段、第几轮、确认消息正文、状态（排队 / 已发送 / 通过 / 修改 / 放弃）、本人回复、入队和回复时间 | 状态为「已发送」的全局最多一条 |
| `item_links` | 条目、关联条目、关系（重复 / 补充 / 修订 / 演进 / 矛盾）、`changed_facts`、状态（有效 / 未定 / 已裁决 / 未采纳）、来源线程、确认或裁决编号 | 见 [10](10-历史检索与上下文.md) 第 9 节 |
| `field_history` | 条目或待办的字段历史：字段、值、生效和失效时间、取代来源、依据消息、确认编号 | 旧值不删除。项目和产品的字段历史在 `object_history` |
| `qa_log` | 问题、回答、`cited`、`scope`、对应的模型调用 | — |
| `todo_sources` | 待办、来源片段、来源条目 | 一条待办可以来自多个片段（`same_as` 时追加） |
| `changes` | 线程编号、对象、字段、改前、改后、原因（模型判断 / 本人指令） | 「撤销」按它恢复 |
| `corrections` | 时间、改动类型、对象、改前、改后、涉及标签、来源 | — |
| `memory_rules` | 规则文本、触发标签或关键词、来源纠正、状态（提议 / 已确认 / 已拒绝 / 已覆盖）、确认时间 | — |
| `entity_cards` | 标签、卡片字段、更新时间 | 标签唯一。只用于客户、供应商、人员 |
| `objects`、`object_aliases`、`object_links`、`item_objects`、`object_history`、`objects_fts` | 项目和产品对象，见 [09](09-对象清单.md) 第 8 节 | — |
| `model_calls` | 见第 1.5 节 | 默认 30 天后清理 |
| `items_fts` | 条目标题、摘要、标签文本、所含附件的提取文本 | FTS5 `trigram`，随条目同步 |

`items` 增加 `thread_id`、`prompt_versions`；`todos` 增加 `due_derived_from`、`confidence`、`replaced_by`；`segments` 增加 `content_hash`（原样重发检测）。

## 3. 实施步骤

替换 [02](02-技术路线.md) 第 11 节的步骤 4–7。步骤 1–3（长连接、转发实测、片段器）不变，步骤 8（附件）不变。每步通过才进下一步。

| 步骤 | 做什么 | 怎样算通过 |
| :--- | :--- | :--- |
| A 骨架 | 片段处理图全部节点和五个确认点，模型节点先用假判断函数（返回固定结果，按意见重做时返回另一组固定结果）；检查点；确认队列；revise 的回退跳转；启动时恢复；`threads`、`reviews` 表。另外单独实测百炼 | 假判断下片段经五次「通过」后走完落库、存档、回执；任一阶段回「改：…」后该阶段重做并重新确认，回退到更早阶段时后面的阶段重新逐个确认；「全部通过」后不再停下；「放弃」后业务库无写入、片段进未归类；两个片段同时到达时确认消息排队，一次只发一条；原件库里有每个附件、同一文件重发只存一份；当日完整对话记录里收发两个方向的消息都在；事项文件夹里的附件链接都能打开；在阶段 3 等待确认时杀进程，重启后确认仍有效、回复后继续，前面的节点不重跑。百炼实测：`qwen3.8-max` 经 Pydantic AI 能完成「思考模式 + 查询工具 + 结构化输出」的一次调用 |
| B 主线 | intent、split、classify、extract 接真模型；judge 仍用假函数（全部判为新事）；全部节点内核验；fallback | 回归样例：报价加招聘切成两条并分别归 `sales`、`hr`；各领域样例分类正确；数字保真 100%；单句「这是项目交付」被判为纠正；核验退回后重做成功的案例在 `model_calls` 里可见 |
| C 历史判断 | recall、实体卡片、judge、revise 接真模型；`item_links`、`todo_sources`、`changes`；「撤销」 | 两周前出现过的客户在阶段 2 命中已有标签；简称确认一次后下次直接归并；换了说法的同一件事挂到旧条目下，不新建待办；交期改动判为修订，旧值进字段历史；数量说法冲突判为矛盾并在阶段 2 列出双方原文；召回里没有的 80 天前旧事由 judge 用工具查到；「方案发过去了」在阶段 4 列为标完成；意见「第一件主领域是项目交付」重做后满足约束，「面试那件不用记」回退到阶段 1；「撤销」恢复最近一次写入 |
| C2 项目与产品清单 | 对象表；recall 召回对象；judge、extract 的对象输出；清单文件和对象页生成；对象类纠正；「项目清单」「产品清单」「查 项目名」 | [01](01-需求说明.md) 第 11 节验收 16–18；新子项目挂到正确上级；参数新值保留历史；合并两个重复产品后记录和关联全部转移；60 天无动态的项目出现在周提醒里 |
| D 纠正 | 纠正图、reconcile、`corrections` | 「拆开」「并到上一段」后已完成的待办不复活、不重复；改领域后存档文件移到新目录；自然语言纠正与固定指令效果相同 |
| E 规则与问答 | 规则提议图、问答图、`memory_rules` | 同类纠正两次后收到规则提议，确认后同类内容直接分对；「上周和某某谈到哪一步」返回带编号引用的回答，编号都在工具结果里；[01](01-需求说明.md) 第 11 节验收 19–21；[10](10-历史检索与上下文.md) 第 8 节样例全部通过；工具结果超过上限时压缩生效，`model_calls` 里可见 |
| F 每日清单 | 清单模板与定时任务 | 按 [06](06-纠正查询与清单.md) 第 5 节的顺序推送，含等待回答的问题和规则提议 |

**回归样例**：

- 每个模型节点一套（`tests/judges/`），样例是该节点的输入上下文加期望输出。初始每个节点 15–20 个，覆盖 [07](07-上下文提示词与核验.md) 第 2.2 节的示例情况。
- 端到端一套（`tests/e2e/`），样例是片段加期望的数据库写入，覆盖 [01](01-需求说明.md) 第 11 节与分析相关的验收项。
- 全部用虚构名称和数字，可以进 Git。线上分错的案例从 `model_calls` 导出、去敏后加入。
- 指标：意图准确率、切分正确率、对象与关系判断准确率、领域准确率、待办精度与召回、数字保真率（必须 100%）、各阶段一次通过率（本人第一次就回「通过」的比例）、每段平均重做轮数、意见约束一次满足率。一次通过率低的阶段，就是下一步要改提示词或上下文的地方。
- 改提示词、换模型版本、升级框架，先跑相关节点和端到端回归，指标不退步才切换。

## 4. 风险

| 风险 | 应对 |
| :--- | :--- |
| 一段要经过 5 次思考模式调用，回执要等一两分钟 | 先回「已收到 N 条，整理中」；评测各节点关闭思考后的准确率，不退步的关闭 |
| 每段要确认 5 次，转发多时确认排长队 | 「全部通过」一键放行当前片段；每个阶段可在配置里单独关闭确认（关闭的阶段结果仍出现在写入计划里）；按各阶段一次通过率决定哪些阶段先关；清单显示排队数 |
| 本人一时没空回复，后面的片段都在排队 | 没有超时，原件都已保存，不会丢；排队期间各片段已跑到自己的第一个确认点，回复后很快推进 |
| 自由文本被误判为对当前确认的意见，或反之 | 以「改：」开头的消息不经模型判断；意图拿不准时按新内容处理；误判会体现在下一条确认消息里，本人可以放弃或再说一遍 |
| 模型把进展误判为完成 | 阶段 4 逐条列出要标完成的待办，本人通过才写入；写入后仍可「撤销」 |
| 百炼兼容接口对思考模式加工具调用的支持不完整 | 步骤 A 实测。不行时：无工具的节点改用 JSON 输出模式；judge 改为「召回更充分、不开工具」 |
| 检查点和模型调用记录含正文 | 只在服务器本地；与业务库同等保护；30 天清理；导出样例必须去敏 |
| 框架升级改变行为 | 版本钉死；升级走回归 |
| 历史变多后召回不全、模型查不到 | 召回宁多勿漏；judge、answer 可用工具往深处查；回答写明查过的范围；查不到的案例导出为回归样例，改召回或工具 |
| 工具循环过长、上下文变乱 | 工具调用上限（judge 8 次、answer 15 次）；单次返回分页；循环内压缩；长附件只经 `read_long` 进入 |
| 两个框架的学习成本 | 两者各守一层（[04](04-工作流总览.md) 第 6 节），节点代码不混用 |

## 5. 默认决定

下面这些先按此执行。若与实际情况不符，改本文后再做。

- 编排用 LangGraph，检查点存 SQLite；模型节点用 Pydantic AI；节点里不用 LangChain 的模型和 Agent 类。
- 片段处理图五个模型节点：意图、切分、历史判断、分类、抽取。语义判断都在这些节点里，不用相似度阈值下结论。
- 片段处理分 5 个阶段，每个阶段经本人确认才进入下一阶段，默认全部开启；有意见按意见重做直到通过，可回退到更早阶段；确认没有超时；一次只发一条确认。数据只在「写入计划」通过后写入。
- 模型不写数据；业务数据只由代码节点写入，并留变更记录。
- 模型只用 `qwen3.8-max`，判断节点开思考；回归评测锁快照 `qwen3.8-max-0902`。
- 检索用标签匹配加 SQLite FTS5 `trigram`，不上向量库。若「换种说法就召回不到」成为常见问题，再加向量召回并在本文记录。
- 规则只来自本人说过或确认过的内容。
