每个模型节点在 [05](05-片段处理图.md)、[06](06-纠正查询与清单.md) 里写了契约。本文说明三件所有节点共用的事：上下文从哪来、按什么顺序放（第 1 节）；提示词文件怎么组织、怎么改（第 2 节）；核验规则写在哪、怎么回灌（第 3 节）。

## 1. 上下文

### 1.1 三种记忆

| 记忆 | 存什么 | 谁写入 | 谁读 |
| :--- | :--- | :--- | :--- |
| 经历 | 片段原文、条目摘要卡、待办、条目之间的关系（重复 / 补充 / 修订 / 演进 / 矛盾）、字段历史、附件提取文本。分层和取用方式见 [10](10-历史检索与上下文.md) 第 2、3 节 | 片段处理图的 commit | recall 召回摘要层；judge、answer 用工具逐层往下查 |
| 项目与产品 | 对象清单：字段、状态、上下级、关联、状态和参数历史（[09](09-对象清单.md)） | 阶段确认通过后由代码写入；统计字段由代码更新 | recall 召回；judge、classify、extract；问答用工具查 |
| 对象 | 客户、供应商、人员每个标签一张实体卡片：标准名、别名、种类、常见领域、最近 3 次提到的日期和一句话、相关联系人、关键参数 | commit 之后由代码增量更新；别名只写本人确认过的 | judge、classify |
| 规则 | 本人确认过的规则：一句话加触发条件 | 规则提议图（[06](06-纠正查询与清单.md) 第 3 节） | judge、classify、extract |

模型自己总结的「经验」不写入任何一种记忆。只有本人说过或确认过的才进规则。

### 1.2 每个节点看什么

| 节点 | 定义与原则 | 本人规则 | 实体卡片 | 历史 | 待办 | 本次内容 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| intent | 意图种类和判断原则 | — | — | 最近 3 次回执要点 | — | 片段原文、当前等待确认的那一条 |
| revise | 阶段划分和意见解读原则 | — | — | — | — | 各已完成阶段的结果、本人这条意见、本线程之前的意见 |
| split | 切分原则 | — | — | 同会话最近 3 个片段标题 | — | 片段原文 |
| judge | 「同一对象」「同一件事」的判断原则；「什么算项目」、对象层级规则；六种新旧关系的定义 | 与候选标签相关的 | 候选标签的；候选项目和产品的对象摘要及上下级 | 候选历史条目的摘要卡，更多由工具查 | — | 事项原文 |
| classify | 领域、类型定义，必抽字段表 | 与已认定标签相关的 | 已认定标签的；已确认对象的摘要 | 有关系的条目的领域 | — | 事项原文、备注 |
| extract | 待办、决定、摘要的要求；对象字段和状态的取值表 | 与已认定标签相关的 | 已确认对象的当前状态、关键日期和参数 | 阶段 2 确认过的关系，有关系的条目摘要卡 | 候选未完成待办 | 事项原文、备注、分类结果、今天日期 |
| reconcile | 配对原则 | — | — | — | 旧待办 | 新待办、事项原文 |
| answer | 作答原则；新旧关系怎么用（[10](10-历史检索与上下文.md) 第 4.5 节） | 与问题提到的名字相关的 | 召回的对象摘要，更多由工具查 | 召回的摘要卡，更多由工具查 | 由工具查 | 问题、今天日期、上一轮问答 |
| draft | 规则写法 | 已有规则（查冲突） | — | — | — | 这组纠正记录 |

原则：给模型足以做出判断的信息，而不是能找到的全部。判断「以前做没做过」所需的历史，必须由 recall 召回放进上下文，或者开工具让模型自己查，不能指望模型记得。召回只给目录和摘要；工具、单次返回上限、循环内压缩见 [10](10-历史检索与上下文.md) 第 3、5 节。

**按意见重做时多两块。** 节点因本人的修改意见被跳回重做（[05](05-片段处理图.md) 第 3.4 节）时，在「本次任务说明」之前加：

```text
【上一版结果】   这个节点上一次的输出（原样）
【本人的意见】   这一阶段收到的全部意见，按时间顺序，最新的在最后；附 revise 整理出的约束
```

任务说明相应改为：「本人对上一版有意见。以本人意见为准，只改意见涉及的部分，其余保持不变；在 `applied_feedback` 里用一两句话说明改了什么。」前面阶段已确认的结果，作为「上一步的结果」照常提供，并注明「已经本人确认」。

### 1.3 顺序和标注

```text
[system]  定义与原则（提示词文件，固定）
[system]  本人规则（随确认累积）
[user]    实体卡片 → 历史 → 待办 → 上一步的结果 → 本次内容 → 本次任务说明
```

- 固定的在前、变化的在后、本次内容和任务说明放最后。
- 每个区块有标题，并写明来源和用途，例如「【候选历史条目】由系统检索，可能不相关，以原文为准」。
- 编号原样给出（条目 #231、待办 #57），要求模型引用编号而不是复述标题，便于核验。
- 每个区块有条数上限（[05](05-片段处理图.md) 第 4.4 节），目的是让模型看得清楚，不是为了省钱。

### 1.4 长片段

片段超过 40 条消息或 6000 字时，split 先看全文切事项；后续节点每个事项只拿自己范围内的原文和备注，一般不会超长。单个事项仍超长时，按时间切块，每块由一个模型步先出 200 字以内的提要；送给后续节点的是开头、结尾若干条原文加中间各块提要。对话记录文件始终存全文。

## 2. 提示词

### 2.1 文件组织

每个模型节点一个提示词包，版本化，不写在代码里：

```text
prompts/
  intent/v1/
    system.md          定义、原则、禁止事项
    task.md            本次任务说明模板（占位符由代码填）
    examples/          3–5 个虚构示例及期望输出
    CHANGELOG.md       相对上一版改了什么、为什么、评测结果
  split/v1/
  judge/v1/
  classify/v1/
  extract/v1/
  reconcile/v1/
  revise/v1/
  answer/v1/
  draft_rule/v1/
  chunk_summary/v1/
```

- 输出结构不在提示词包里手写。它就是代码里的 Pydantic 模型，Pydantic AI 自动把它交给模型；提示词里只说明各字段的含义和填写要求。
- 启用哪个版本写在配置里。每次模型调用的记录里带上节点名和提示词版本。
- 改提示词的流程：复制为新版本目录，修改，跑该节点的回归样例（[08](08-选型与实施.md) 第 3 节），不退步才改配置。旧版本保留，可以回滚。

### 2.2 怎么写

| 部分 | 要点 |
| :--- | :--- |
| 定义 | 用表格。领域、类型用「中文名 + 代码」并列，输出只允许代码 |
| 原则 | 用「当……时，……」句式，并配一个反例。例：「当事项只是汇报已有待办的进展时，填 `same_as`，不新建」 |
| 不确定 | 每个节点都写明不确定时往哪放（`unsure`、`confidence`、理由），并写「不确定就说不确定，不要猜」 |
| 禁止事项 | 「原文没有的数字、日期、人名不要写」放在 `system.md` 显眼处，在 `task.md` 末尾再写一次 |
| 工具 | 有工具的节点写清什么情况该查、什么情况不该查。例：「候选里已有的条目不要再查」 |
| 示例 | 来自回归样例，名称和数字全部虚构。覆盖该节点最容易错的情况 |

各节点示例必须覆盖的情况：

| 节点 | 示例覆盖 |
| :--- | :--- |
| intent | 转发加备注；单句纠正；进展汇报；混合内容；对当前确认的意见与新内容的区分 |
| revise | 意见针对当前阶段；意见针对更早阶段（在分类阶段说「应该拆成两件」）；意见含明确取值；意见含糊（「不太对」） |
| split | 一段两件事；「好的」接上一段；备注在末尾 |
| judge | 简称命中；同名不同对象；换了说法的同一件事；看似相关其实是新事；新子项目挂到已有项目下；一次性小事不建项目；型号挂到产品下；交期改了判为修订；两种说法冲突判为矛盾；同一份文件再发一次判为重复；召回里没有的旧事用工具查到 |
| classify | 跨领域归最终负责交付的一块；备注改变领域；补充旧事但领域变了 |
| extract | 新建；同一待办换说法；报告完成；相对日期；原文没有截止日期；「验收通过」引起项目状态变化；产品参数出现新值 |

### 2.3 模型参数

- 模型 `qwen3.8-max`，回归评测时锁定快照 `qwen3.8-max-0902`。
- 判断节点（split、judge、classify、extract、reconcile、draft）开启思考模式。intent 和 answer 初期也开启，评测后若关闭不影响准确率再关闭，以缩短回执等待时间。
- 温度取低值；开启思考时不同时改 `top_p`。
- 结构化输出用 Pydantic AI 默认的工具调用方式（把输出结构作为一个工具交给模型），这样同一个节点里查询工具和结构化输出可以共存。百炼对「思考模式 + 工具调用」的支持在实施第一步实测（[08](08-选型与实施.md) 第 3 节步骤 A）。

## 3. 核验

核验全部是代码。按位置分两层：

| 位置 | 实现方式 | 失败时 |
| :--- | :--- | :--- |
| 节点内 | 该节点 Agent 的输出核验器 | 抛 `ModelRetry`，错误原因发回模型重做，最多 2 次；仍失败则把失败原因写进确认消息，由本人给意见或放弃 |
| 节点间 | 片段处理图的 check 节点（[05](05-片段处理图.md) 第 4.8 节） | 不退回模型；把问题写进阶段 5 的确认消息，由本人决定 |

### 3.1 通用核验

| 核验 | 规则 | 用于 |
| :--- | :--- | :--- |
| 结构 | 符合 Pydantic 模型；枚举值在代码表内 | 全部节点 |
| 编号存在 | 输出引用的标签、条目、待办、问题、片段编号必须出现在本节点的上下文或本次工具结果中 | intent、judge、extract、reconcile、answer、draft |
| 数字保真 | 从输出文本中抽出所有数字（含全角、中文数字、「万」「千」、百分号、日期），归一化后必须能在原文或本人备注中找到 | classify、extract、answer（对照工具结果） |
| 片语保真 | `due_derived_from` 等「依据」字段必须是原文子串；`changed_facts` 的旧说法是旧条目原文或摘要卡的子串，新说法是本次原文的子串 | extract、judge |
| 冲突必提 | 引用的条目中有「未定」冲突时，`conflicts` 不能为空 | answer |
| 范围说明 | 基于工具查询的输出必须填写查过的范围；达到工具调用上限时写明没查到的部分 | answer、judge |
| 范围 | 消息序号不越界、不重叠、覆盖全部消息 | split |
| 理由 | 判断类字段（`relation`、`unsure`）必须附非空理由 | judge |
| 满足意见约束 | 按意见重做时，revise 整理出的每条约束（字段路径 = 取值、事项数量、某段消息归属）必须在新输出中成立；本人意见里给出的数字和日期视同原文 | 被跳回重做的节点 |
| 说明改动 | 按意见重做时 `applied_feedback` 不能为空，且新输出与上一版必须有差异 | 被跳回重做的节点 |

### 3.2 回灌的错误信息

错误信息要具体到字段和值，并给出改法，例如：

- 「`items[1].domain` 的值 `销售` 不在代码表内。允许值：sales、delivery、rnd、supply、finance、hr、it、other。」
- 「`summary` 中的『12.5 万』未在原文出现。删除它，或改用原文中的写法。」
- 「`todos[0].same_as` 为 #88，但 #88 不在候选待办里。候选为 #57、#61。」

### 3.3 发现不了的错误靠什么兜底

核验只能查字面上可核对的事。领域分错、两件事被判成一件，代码查不出来。兜底是：

1. 每个阶段的结果都经本人确认，模型拿不准的地方在确认消息里标「（拿不准）」；
2. 本人提意见，按意见重做直到通过；写入之后发现问题，用纠正图改；
3. 确认意见和纠正都记录下来，同类累计两次变成规则（[06](06-纠正查询与清单.md)）；
4. 分错的案例导出为回归样例，离线修复（[00](00-工作流设计系统提示词.md) 第 4 节第 4 层）。
