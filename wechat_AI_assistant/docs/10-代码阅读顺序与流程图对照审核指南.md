## 一、 推荐的四步代码阅读顺序（由浅入深，对照图纸不迷路）

不建议按文件名字母顺序读（例如一上来打开 1081 行的 storage/db.py 或 2233 行的 index.html 会陷入底层细节，看不见主流程）。最省力的审核方式是打开全景图，按「先看数据与提示词契约 → 再顺着主图从左往右走主干 → 再查分支工具 → 最后查存储与网页」分四步走读：

### 第一步：先读「词汇表与静态契约」（3 个文件，约 15 分钟）

目的：还没看流程逻辑前，先把系统里流转的数据包格式、模型档位和给大模型的规矩看明白。

1. src/wechat_assistant/schemas.py（109 行，建议通读全文）
   - 第 11–36 行：WorkDomain（6 大业务板块）、ListType（4 类清单：项目行动、日常行动、想法池、等待他人）、PriorityLevel（P0–P2）。
   - 第 39–63 行：IntentRoute（阶段三路由器必须输出的 JSON 结构，含 12 个意图枚举值、置信度、补全后文本、检索词、澄清问题）。
   - 第 66–99 行：EvidenceCard（阶段四压缩后的证据卡）、ActionMutation 与 TriageProposal（路径④主推模型起草的待确认提案结构，注意第 86 行 estimated_hours 默认值为 0.0）。
   - 第 102–109 行：CriticVerdict（路径④审计结论结构，含 passed 与 fix_instructions）。

2. src/wechat_assistant/prompts/system_prompts.py（66 行，建议通读全文）
   - 全系统所有大模型提示词都集中在这 66 行里，没有藏在其他业务文件里：
     - 第 3–23 行 FAST_ROUTER_PROMPT：阶段三路由分诊规则（含默认禁止联网调研规则）。
     - 第 25–38 行 PRODUCER_TRIAGE_PROMPT：路径④第 3 步方案起草规则（日历跨度优先、不猜工时、不代写调研正文）。
     - 第 40–45 行 CRITIC_AUDIT_PROMPT：路径④第 4 步异构审计 4 条底线。
     - 第 47–51 行 QA_GROUNDED_PROMPT：路径③查档闭卷引用规则。
     - 第 53–58 行 CONVERSATIONAL_ADVISOR_PROMPT：路径②参谋单轮回复规则。
     - 第 60–66 行 EPISODE_SUMMARY_PROMPT：阶段六每 8 轮后台滚动摘要合并规则。

3. src/wechat_assistant/config.py（464 行，重点读两段即可）
   - 第 38–204 行 Settings：看清三档模型默认配置（fast=qwen3.8-flash 备选 qwen-plus；producer=qwen3.8-max 备选 qwen-max；critic=deepseek-v4-pro 备选 qwen3.8-max）、邮件白名单默认值（V&F、Tera、B&D）以及外部搜索默认关闭（external_search_enabled=False）。
   - 第 207–228 行与第 394–464 行：看 assert_no_secrets_leaked 如何在每次输出前拦截密钥泄漏，以及 DashScopeLLMGateway.generate_structured 如何在主模型报错时自动重试并切换到备选模型。

### 第二步：顺着全景图从左到右走完「主干流水线」（5 个文件，核心审核区）

目的：把全景图从左上角「开始」一路核对到「本次结束」和「阶段五」。

4. src/wechat_assistant/web/app.py（先读第 143–415 行，Web 驾驶舱接口留到第四步）
   - 第 268–342 行 create_app 与 lifespan：看单进程服务启动时如何装配数据库、OneDrive、大模型网关、企微网关，并在后台拉起阶段六的两个常驻任务（第 321 行早晚简报定时器、第 334 行邮件轮询循环）。
   - 第 380–415 行 wecom_verify_url 与 wecom_callback_post：微信消息到达服务器的 HTTP 第一站，解密后用 asyncio.create_task 异步派发并立即返回 success。
   - 第 217–265 行 run_turn_with_heartbeat：对照图上的「进度心跳」说明框，看它如何监控单次处理耗时，满 12 秒推第一次阶段提示、此后每 25 秒推一次。
   - 第 143–215 行 build_daily_digest_message 与 _daily_digest_scheduler：对照阶段六早晚简报与 18:00 进度盘点。

5. src/wechat_assistant/intake/wecom_gateway.py（625 行）与 src/wechat_assistant/intake/mail_poller.py（130 行）
   - 对应全景图「阶段一｜接收与预处理」前半段：
     - wecom_gateway.py 第 464–490 行 handle_callback_event：主入口消息去重、0.5 秒内推「已收到」回执、XML 解析后送入聚合器。
     - wecom_gateway.py 第 544–595 行 sync_and_dispatch_kf：备用客服通道拉取消息、第 577–583 行强制执行 owner_external_userid 单人白名单、第 516–541 行展开微信原生合并转发卡片。
     - wecom_gateway.py QuietAggregator：连续逐条转发停手 2 秒自动合并成一次处理；发「好了」立即结束等待。
     - wecom_gateway.py 第 303–362 行 _transcribe_audio_dashscope：调用 qwen3-asr-flash 把语音转文字。
     - wecom_gateway.py 第 597–625 行 _handle_flushed_kf_batch：调用引擎处理，拿到回复后做密钥脱敏并推回微信。
     - mail_poller.py 第 1–130 行（全文很短）：看 matches_mail_allowlist 白名单过滤、mark_seen 持久去重、wrap_untrusted_email 不可信标签包裹。

6. src/wechat_assistant/context_assembler.py（356 行，通读第 135–356 行）
   - 对应全景图「阶段二｜装配上下文」：
     - 第 144–260 行 ContextAssembler.assemble：逐段核对 Layer 1（跨天滚动摘要 + 最近 30 轮对话 + 30 分钟间隔线）、Layer 2（待确认卡片 + 60 分钟新鲜度）、Layer 3（最多 3 张关联项目卡自动挂载 + 30 个项目 + 60 条未完待办 + 20 条个人规则）。
     - 第 262–272 行 ContextAssembler.render_for_router：核对送进阶段三路由器的 7 段固定拼装顺序。
     - 第 274–356 行 ContextAssembler.retrieve_long_horizon_evidence：核对 Layer 4（路径③和路径④才触发的文档全文索引 + 历史旧对话检索）。

7. src/wechat_assistant/graph.py（1234 行，全流程核心总控，建议按下面 4 小段跳读，最清晰）
   - 第 1 小段（先看总入口）：handle_incoming_turn 与 _handle_incoming_turn_inner。加可重入锁串行保护心跳回调后，直接进入 LangGraph；不再因看板、负荷、撤销、开始、完成、1/2、改：提前返回。正常结束或异常崩溃都调用 _record_turn_pair 记录对话。
   - 第 2 小段（看状态图连线蓝图）：第 904–967 行 _route_after_router、_route_after_critic、_build_graph。这 64 行代码就是全景图阶段三和阶段四的拓扑连接表，所有节点和有向边一目了然。
   - 第 3 小段（顺着蓝图逐个核对阶段三与阶段四的 10 个节点函数）：
     - 阶段三：第 337–433 行 _node_guardrail_router（调用 qwen3.8-flash + 硬编码兜底规则）。
     - 路径①：第 435–534 行 _node_action_shortcut（确认/作废卡片、一句话多条批量打卡、单条开始/完成、撤销）。
     - 路径②：第 536–558 行 _node_conversational_responder（单次模型调用回复参谋意见，不建待办）。
     - 路径③：第 560–640 行 _node_quick_qa_responder（检索文档页码与旧对话，无依据直接拒答，有依据带出处回复）。
     - 路径⑤：第 892–901 行 _node_clarify_or_unsupported（能力边界说明或追问澄清，不建待办）。
     - 路径④五步：第 642–701 行 _node_react_investigator（含第 272–333 行 _ingest_attachments_and_source 提取附件与备份原件）→ 第 703–733 行 _node_context_compactor → 第 735–825 行 _node_producer_drafter → 第 827–876 行 _node_heterogeneous_critic → 第 878–890 行 _node_hitl_preview_gate（存待确认卡并格式化微信决策卡）。
   - 第 4 小段（看阶段五确认落盘与后台滚动摘要）：第 971–1044 行 commit_pending_proposal（铸造令牌、过门禁、归档附件、原子写库、重绘 5 份看板）；第 170–259 行 _record_turn_pair 与 _refresh_semantic_summary（记录本轮对话，每满 8 轮后台刷新滚动摘要）。

### 第三步：核查阶段四与阶段五调用的「受控工具箱与门禁」（8 个小文件，约 20 分钟）

目的：确认主流程里调用的每个工具函数都是纯确定性代码或带安全护栏的受控操作，没有任何越权能力。

8. src/wechat_assistant/storage/extractors.py：核查 PDF、Word、Excel、CSV/TSV、ZIP（最多 30 个文件、50MB 上限、防路径穿越）提取逻辑，以及加密/损坏文档与 .dwg 二进制文件的安全占位返回。
9. src/wechat_assistant/nodes/critic_rules.py（67 行）：核查路径④第 4 步先于大模型执行的硬编码数字保真检查与外部等待工时检查。
10. src/wechat_assistant/tools/schedule_tools.py（56 行）：核查工作日推算与未来 14 天排期密度检查（每日 >= 5 项标为拥挤，不猜测个人净工时）。
11. src/wechat_assistant/tools/memory_tools.py（44 行）：核查混合检索、按页读取、项目时间线三个只读函数。
12. src/wechat_assistant/tools/guard.py（56 行）：核查 ApprovalToken 的 HMAC-SHA256 签名与 before_tool_callback 写操作拦截门禁。
13. src/wechat_assistant/tools/onedrive_tools.py（276 行）：第 20–133 行看 5 份云端 Markdown 看板如何纯从 SQLite 渲染；第 136–276 行看世纪互联 OneDrive 小文件直传、>=4MB 分片上传、上传后清理本地缓存与同步全部看板。

### 第四步：最后核查「底层数据库与 Web 驾驶舱」（2 个文件，按需抽查）

16. src/wechat_assistant/storage/db.py（1081 行，重点抽查 4 段）：
    - 第 68–245 行 _init_schema 与 mark_external_seen：10 张核心表 + 2 张 FTS5 索引表定义、启动时自动清理历史重复索引、外部消息 ID 去重表。
    - 第 477–603 行 apply_proposal_atomic 与 undo_last_commit：阶段五如何一次性写入项目与待办、保存 undo_snapshots，以及 24 小时内如何完整回滚。
    - 第 802–854 行 start_item 与 complete_item：开始/完成打卡如何记录实际起止时间、计算 actual_span_days 完成跨度天数并写入 memory_rules 跨度基线。
    - 第 1047–1081 行 dashboard_overview：Web 驾驶舱与早晚简报共用的汇总查询。
17. src/wechat_assistant/web/app.py（第 77–140 行、第 418–557 行）与 src/wechat_assistant/web/static/index.html（2233 行）：
    - 在 app.py 看 AuthManager（微信 6 位验证码、限流、180 天 HttpOnly Cookie）以及 /api/dashboard/overview、/api/items 等受保护接口如何在网页修改数据后自动触发 _sync_onedrive_async 重绘云端看板。
    - index.html 为纯前端展示与交互界面，无业务逻辑分流，可最后浏览。
