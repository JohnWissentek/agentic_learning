你把一段客户对话转发给机器人。服务器把连续到达的消息收成一个片段，然后开始处理：看出有几件事，对照以前的记录，标上领域，抽出待办，给出文档分类归档存储方案。每做完一步，它停下来等你回复。你可能隔几小时才回。用户确认后具体执行。

这段处理要记住走到哪一步。其中某几步要问模型，并拿回一份填好的结果。

走到哪一步，用 LangGraph。问模型并拿回结果，用 Pydantic AI。

## 1. 一次转发里，它们出现在哪

下面用片段 `1024` 走一遍。没有标出框架的步骤，是普通代码。

```text
你转发的消息到达
    代码按消息编号去重，把原件存下来，收成一个片段
    LangGraph 为这个片段开工，编号 seg:1024
        load        代码读出这段消息
        intent      调用判断函数。Pydantic AI 问模型：这是工作内容、提问、纠正，还是闲聊
        split       再问一次：里面有几件事
        review      LangGraph 停下，把「理解」发给你
        你回「通过」。LangGraph 从停下的地方继续
        recall      代码按名字找出可能相关的历史
        judge       判断函数再问模型。模型可以几次查旧记录，然后交出关系
        review      再停下，把「关联」发给你
        classify    判断函数问：归哪个领域
        extract     判断函数问：有哪些待办、决定、摘要
        check       代码列出将要写入的计划
        你确认计划之后
        commit、archive、reply
                    代码写入业务库，写入存档，发回执
    这次处理结束
```

「完成 3」「查 某某」「好了」由接入层直接执行。接入层是收消息的那一段代码。这几句没有分支，也不问模型。

## 2. LangGraph 记住走到哪

LangGraph 把这次处理写成一张图。图上的一步叫节点。节点之间的箭头叫边，表示这一步做完去哪。四张图的形状都是事先写好的。模型只在节点里面回答问题，不改图的形状。

一次开工叫一个线程。四张图各有各的线程编号：

| 图 | 线程编号 | 什么时候开工 |
| :--- | :--- | :--- |
| 片段处理图 | `seg:<片段编号>` | 一个片段收齐 |
| 纠正图 | `fix:<纠正编号>` | 要改已经写入的结果 |
| 问答图 | `ask:<片段编号>` | 意图判断这是一个提问 |
| 规则提议图 | `rule:<提议编号>` | 同类纠正累计两次，或你发「规则：」 |

你说「拆开」或「并到上一段」时，纠正流程把片段处理里从切分到抽取的节点再跑一遍。同一段节点嵌进来用，不另写一份。嵌进来的这一段叫子图。

### 2.1 一份状态

每个线程有一份状态。状态写成固定结构，里面有片段编号、每一步的结果、现在第几轮确认、你的意见。节点是一个函数：它读这份状态，返回要写回去的新字段。

你在确认时的回复决定下一条边。你回「通过」，进入下一步。你提出修改意见，跳回那一步重做。你回「放弃」，这次处理结束，业务库不写。这些边是写好的代码，看的是回复落到状态里的哪个字段。

### 2.2 每步结束都存盘

每个节点跑完，LangGraph 把整份状态写入 `data/checkpoints.db`。这份文件叫检查点。业务数据在另一个文件 `data/app.db`。

分类做完、待办还没做的时候进程崩溃。重启后从分类之后继续。意图、切分、历史判断不再问模型。

停在确认点时，你几小时后才回复。状态还在，从确认点继续。

要回看时，检查点里有每一步当时的状态。模型当时看到的原文记在业务库的 `model_calls` 表里。

检查点里有对话正文，和业务库一样只放在自己的服务器上。已经结束的线程，检查点默认 30 天后删除。删除检查点时，原件和归档还在。

进程启动时，还没结束、也没停在确认点的线程，从最后一个检查点继续。已经停在确认点的线程不动。已经发出的确认消息不重发。

### 2.3 停下来等你

每个阶段结束都有一个 review 节点。阶段是你确认的单位。片段处理有五个：理解、关联、分类、待办与摘要、写入计划。

review 节点调用 `interrupt()`。调用之后，这个线程暂停，函数不再往下走。确认消息交给接入层排队发送。一次只发一条，这样你回「通过」时，对得上是哪一条。

你的回复到达后，接入层用 `Command(resume=回复内容)` 让这个线程从 `interrupt()` 的下一行继续。`interrupt()` 的返回值就是这句回复。线程编号对得上，所以隔几小时仍是同一次处理。

你回「放弃」时，边走到结束，业务库不写。原件在消息到达时已经进了原件库。

图拿到的是一份已经检查过的结果，然后按里面的字段选择下一步。金额在不在原文里、领域代码在不在表里，都在节点内部检查完。

写入业务库的是图里的代码节点 `commit` 和 `apply`。检查点和业务库不一致时，以业务库为准。`commit` 用线程编号认出同一次处理。崩溃后重跑，不会把同一条记录写两次。

## 3. Pydantic AI 问一次模型

图上要问模型的节点，调用一个判断函数。判断函数把材料递进去，拿回一份填好的结果。问模型和检查结果都在这个函数里。函数里面用 Pydantic AI 的 Agent 去问模型。Agent 是这一次提问的执行者：它拿着材料，需要时查工具，最后交回结果。

图只看见这个函数。函数不引用 LangGraph，也不知道自己被哪张图调用。换掉其中一个框架，只改对应的那一层。

### 3.1 函数交出的五样东西

每个判断函数都写明这五样。00 第 3.2 节把它们叫契约。

| 项 | 这一次里是什么 |
| :--- | :--- |
| 任务 | 要判断什么。历史判断的任务是：每个名字对应哪个已有对象，这件事和旧记录是什么关系 |
| 上下文 | 代码事先放好的材料：原文、召回的摘要卡、你确认过的规则。重做时再加上一版结果和你的意见 |
| 输出类型 | 一份固定结构。模型按这个结构填，交回的是字段，不是一篇自由文章 |
| 工具 | 只读查询。意图、切分、分类、抽取没有工具。历史判断和问答有 |
| 核验 | 代码检查。数字必须在原文里。引用的编号必须在候选里，或在这次查询的结果里 |

### 3.2 结果不合格，就在这一次里重做

模型交回结果后，先检查字段类型和枚举值，再跑我们写的核验器。核验器看到「摘要里的 12.5 万原文没有」，就抛出 `ModelRetry`。错误原因作为一条消息回到这次对话，模型重新提交。

重做只在这一次判断里面，次数是 2。它不改提示词文件，不改图，不改数据库。两次仍不通过，失败原因写进确认消息。你决定改意见，或放弃。

网络超时、接口报错是另一件事：请求没有完成。这种由 LangGraph 重试这个节点，最多 3 次，每次等待时间按指数拉长。

### 3.3 历史判断可以在这一次里查旧记录

代码先按名字召回一批候选。历史判断和问答还要往下查。同一个 Agent 可以先查，再交结果：

1. 模型要么调用一个只读工具，要么提交最终结果。工具可以查记录、取原文、读附件的一页。
2. 工具是普通 Python 函数。参数从函数签名生成。工具不写库。
3. 提交之后走第 3.2 节的核验。不过就带着错误再提交一次。
4. 工具调用有次数上限，用来防止停不下来。历史判断的 `judge` 是 8 次。问答的上限在 [08](08-选型与实施.md) 第 1.3 节和 [10](10-历史检索与上下文.md) 第 3.3 节。两处数字还没对齐，以将来对齐后的文档为准。

次数用尽时，这次判断用已经拿到的信息提交，并写明查过的范围。长附件不整篇放进上下文。阅读工具 `read_long` 带着一个具体问题去读，只交回结论和页码。`read_long` 自己也是一次判断函数。它不另开一张图。

分类和抽取不查工具。它们要用的历史，历史判断已经找齐，你也确认过。代码把这些材料放进上下文。

### 3.4 问的是哪一个模型

通过 OpenAI 兼容接口接阿里云百炼。`base_url` 是 `https://dashscope.aliyuncs.com/compatible-mode/v1`，模型是 `qwen3.8-max`。密钥放在环境变量里。思考模式用请求里的额外参数打开。

要填的那份结构，也当作一个工具交给模型。模型查完之后，调用这个工具提交结果。查历史和交结果就在同一次判断里。

## 4. 两层怎么交接

历史判断这一步可以看清交接。

代码先查出可能相关的客户、项目，以及近 90 天的条目摘要。这一步是数据库查询。LangGraph 和 Pydantic AI 都不参与。

LangGraph 调用判断函数 `judge`，然后等它返回。模型在函数里查了三次旧记录，这三次仍算图上的同一步。图不会每查一次就走一条边。函数返回后，图才把关系列表写进状态，并存检查点。

接着进入 review，`interrupt()` 把「补充了哪条、修订了哪项」发给你。你还没回复时，模型调用已经结束。线程停在图上。

```text
节点 judge_node 读到状态:
    代码按 07 的规则装好上下文：召回结果、原文、规则
    调用 judge(上下文)
        函数里，Agent 看到上下文
        需要时调用 search_records 等只读工具
        提交 JudgeResult
        核验不过就 ModelRetry，仍在这个函数里
        把 JudgeResult 交回节点
    节点把结果写进状态
图把状态存进检查点，然后走到确认节点
```

这是示意，不是实现。这个节点不写业务库。你确认「写入计划」之后，另一个代码节点才把计划写入 `app.db` 和存档目录。

### 4.1 你回复的时候

确认消息的版式由代码按模板生成。模型不写这则消息。LangGraph 负责停下和恢复。

你回「通过」。`resume` 带回这句回复，边进入下一阶段。这一下不问模型。

你回「改：第一件是项目交付」。图进入 `revise`。`revise` 是另一个判断函数。它读这句话，判断意见说的是哪个阶段，哪些话能写成确定的值。能写成确定值的，代码记成约束。例如领域就是项目交付，截止就是 11 月 5 日。图跳回那个阶段，重新调用原来的判断函数。这一次的材料里多两块：上一版结果，和你的意见。核验器检查新结果满足这些约束。满足了，图再次 `interrupt()`，把重做的结果发给你。

跳回哪一步、何时再停下，由 LangGraph 做。重新判断、按约束检查，由 Pydantic AI 做。

### 4.2 三个地方各存各的

| 存在哪 | 谁写入 | 内容 | 丢了会怎样 |
| :--- | :--- | :--- | :--- |
| `checkpoints.db` | LangGraph | 流程走到哪、各节点的输出 | 没写完的线程要重跑。已经写入业务库的结果还在 |
| `app.db` | 图里的代码节点 | 条目、待办、对象、规则 | 这是要长期留下的业务数据 |
| `data/inbox/`、`data/archive/` | 接入层和存档节点 | 原件和归档文件 | 原件在分析之前就写入。分析失败也不丢 |

## 5. 三个词

| 词 | 指什么 | 处理一个片段时有多少 |
| :--- | :--- | :--- |
| 阶段 | 你确认一次的范围：理解、关联、分类、待办与摘要、写入计划 | 5 个。每个结束，LangGraph 都停下 |
| 模型节点 | 图上的一步，里面调用一次判断函数 | 意图、切分、历史判断、分类、抽取。重做时再加上 revise |
| 模型步 | 向百炼发出的一次请求 | 一个模型节点里可以有多步：查工具，或核验失败后重做 |

检查点按节点保存，不按模型步保存。历史判断里面查了三次，图上仍是这一个节点。这个节点整个返回之后，才写入检查点。

## 6. 为什么两层都留着

这段流程会在中途停下，把确认放进发送队列，几小时后用同一次进度继续。停下用 `interrupt()`，进度用检查点。这是 LangGraph 已有的能力。

每一次判断要解析结果、检查数字、把错误发回模型，还要从函数签名生成工具参数。这是 Pydantic AI 做的。00 第 5 节把这些列为判断层的第 4–7 条。

Pydantic AI 自带 `pydantic-graph`，也能做图，也能保存状态。本项目的流程用 LangGraph，因为中途停下、几小时后继续，是这里要用的能力。

自己写循环的话，暂停、继续、重试、崩溃恢复都要自己保证。重启之后容易把模型再问一遍，或者把你的回复套到另一次确认上。

LangGraph 会带进 `langchain-core`。节点里的模型调用只用 Pydantic AI。节点不调用 LangChain 的模型、提示词或 Agent。重试和结构化输出就只有一套。
