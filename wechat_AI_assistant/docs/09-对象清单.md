系统自动维护三份清单：项目清单、产品清单、文件夹结构清单。前两份是**对象**：有字段、有状态、有上下级、彼此关联，每条记录、待办和附件都挂在相关对象上，可以按层级往下看，也可以顺着关联横向跳。第三份是归档目录的索引。

## 1. 原则：文件只放一处，清单是不同的看法

- 归档仍按「日期 / 领域 / 事项」存一份（[02](02-技术路线.md) 第 8.2 节）。这是物理位置，不随清单变化。
- 项目清单、产品清单、对象页都是**链接视图**：指向同一批事项文件夹、待办和附件，不复制文件。
- 这样一份报价单同时属于「某某二期」项目、关联「XX 传感器」产品，在两边都能找到，但磁盘上只有一份，改一处处处一致。
- 领域和对象是两条独立的分类线：领域回答「这件事归公司哪一块」，对象回答「这件事关于哪个项目、哪个产品」。两者交叉，就能回答「某某二期在采购方面有哪些事」。

客户、供应商、人员第一版仍用标签（[02](02-技术路线.md) 第 8 节、[07](07-上下文提示词与核验.md) 第 1.1 节的实体卡片），不做成带层级的对象。项目通过字段引用客户标签。以后需要时，按本文同样的方式升级。

## 2. 项目清单

| 字段 | 内容 | 谁维护 |
| :--- | :--- | :--- |
| 名称、别名 | 标准名；本人确认过的其他写法 | 模型提出，本人确认 |
| 上级项目 | 层级：项目 → 子项目或阶段，最多两层（如「某某二期」下的「现场安装」） | 模型提出，本人确认 |
| 客户 | 引用客户标签；内部项目为空 | 模型提出，本人确认 |
| 涉及产品 | 关联产品清单中的产品或型号，可多个 | 模型提出，本人确认 |
| 状态 | 商机 / 实施中 / 交付验收 / 售后 / 暂停 / 已结束 | 模型根据原文提出变化，本人确认 |
| 负责人 | 原文中明确的负责人 | 模型提出，本人确认 |
| 关键日期 | 开始、计划交付、验收等原文中出现过的日期 | 模型提出（数字保真），本人确认 |
| 主要领域 | 该项目下各条记录领域的分布，取最多的 | 代码统计 |
| 最近动态、记录数、未完成待办数、文件数 | — | 代码统计 |

**什么算项目（写进提示词）：** 有明确的客户或内部目标、有可交付的结果、会持续一段时间的一件事。一次性的询价、一次面试不建项目，只作为记录。拿不准时不建，由本人在确认时决定。

**状态只按顺序走吗：** 不强制。暂停、恢复、跳过阶段都允许，但每次变化都必须由原文支持（附依据消息），并经本人确认，写入状态历史。

## 3. 产品清单

| 字段 | 内容 | 谁维护 |
| :--- | :--- | :--- |
| 名称、别名 | 标准名；本人确认过的其他写法 | 模型提出，本人确认 |
| 层级 | 产品线 → 产品 → 型号或版本，最多三层 | 模型提出，本人确认 |
| 状态 | 规划 / 研发 / 试产 / 在售 / 停产 | 模型根据原文提出变化，本人确认 |
| 关键参数 | 规格、料号、量程、接口等，每个参数附出处（哪条记录、哪天） | 模型从已确认记录中提出（数字保真），本人确认 |
| 用于哪些项目 | 项目清单「涉及产品」的反向 | 代码 |
| 最近动态、记录数、未完成待办数、文件数 | — | 代码统计 |

同一参数出现新值时不覆盖旧值，按时间保留，对象页显示最新值并列出历史，因为参数变更本身就是研发和采购关心的信息。

## 4. 文件夹结构清单

完全由代码生成，不调模型：

- 归档目录树：日期 → 领域 → 事项，每层标出事项数和文件数；
- 按领域汇总：每个领域最近 30 天的事项数、文件数；
- 「未归类」和「.已替换」文件夹单独列出，便于清理。

## 5. 清单文件长什么样

每次写入后由代码重新生成，放在归档根目录下，不打开数据库也能浏览：

```text
data/archive/
  清单/
    项目清单.md            ← 按状态分组，子项目缩进；每行：名称、客户、状态、最近动态、未完成待办数、链接
    产品清单.md            ← 产品线 → 产品 → 型号；每行：名称、状态、用于几个项目、链接
    文件夹结构.md
    项目/
      某某二期.md          ← 对象页
      某某二期-现场安装.md
    产品/
      XX传感器.md
      XX传感器-V2.md
  2026-10-31/
    ...
```

**对象页**的内容：

1. 基本信息（第 2、3 节的字段）；
2. 上级和下级（链接）；
3. 关联：项目页列出涉及产品，产品页列出用于哪些项目（链接）；
4. 时间线：每条相关记录一行，日期、标题、领域，链接到事项文件夹；
5. 未完成待办；
6. 文件：相关附件的列表，链接到事项文件夹里的文件；
7. 状态历史和参数历史，每条附出处。

清单文件是生成物，手工修改会在下次生成时被覆盖。要改内容，通过机器人会话（第 7 节）。

## 6. 在工作流里怎么维护

按 [00](00-工作流设计系统提示词.md) 第 2 节和第 3.7 节：代码召回，模型判断，本人确认，代码写入。

| 时机 | 做什么 | 谁 |
| :--- | :--- | :--- |
| recall（[05](05-片段处理图.md) 第 4.4 节） | 事项里提到的名字与项目、产品的名称和别名匹配，召回候选对象及其上下级 | 代码 |
| judge，阶段 2 确认 | 每个事项关于哪些项目、哪些产品；提到的名字是已有对象、已有对象的子级，还是新对象；新对象的上级、客户、关联产品 | 模型提出，本人确认。例：「新建子项目『现场安装』，属于『某某二期』」 |
| extract，阶段 4 确认 | 原文显示的对象变化：项目状态（「验收通过」→ 售后）、关键日期、产品参数（「量程改为 0–5000 ppm」），各附依据消息 | 模型提出，本人确认 |
| check，阶段 5 确认 | 写入计划里列出全部对象变更：新建、改字段、改状态、新关联 | 代码汇总，本人确认 |
| commit 之后 | 更新统计字段；重新生成受影响的对象页、项目清单、产品清单、文件夹结构清单 | 代码 |
| 每周一次 | 60 天没有动态、状态不是已结束的项目，列进每日清单问「要结束吗」；名称或别名高度重叠的对象，交给模型判断是否重复 | 代码发现候选，模型判断是否重复，本人决定 |

## 7. 纠正与探索

**纠正**（走纠正图，[06](06-纠正查询与清单.md) 第 1 节，同样逐步确认）：

| 本人说 | 改动类型 |
| :--- | :--- |
| 「这条不是二期的，是三期的」 | 改事项的对象关联 |
| 「现场安装是二期的子项目」 | 改上级 |
| 「二期已经结束了」 | 改状态 |
| 「XX 和 XX-V2 是同一个」 | 合并对象：别名合并，记录、待办、关联全部转到保留的那个 |
| 「二期也用了 YY 模块」 | 加关联 |

**探索**（固定指令由代码执行；自然语言提问走问答图）：

| 本人说 | 返回 |
| :--- | :--- |
| 「项目清单」「产品清单」 | 清单摘要：按状态分组的名称和最近动态 |
| 「查 某某二期」 | 对象摘要：客户、状态、上下级、涉及产品、最近 5 条记录、未完成待办 |
| 「二期用到的传感器最近有什么变化」 | 问答图：模型用 `get_object`、`list_objects`、`related_objects` 顺着关联查，再整理回答 |

## 8. 数据

| 表 | 主要字段 | 约束 |
| :--- | :--- | :--- |
| `objects` | 编号、类型（项目 / 产品）、名称、上级编号、状态、字段（JSON）、创建和更新时间 | 同类型下名称唯一；上级必须同类型；项目最多两层、产品最多三层 |
| `object_aliases` | 别名、对象、是否本人确认 | 别名 + 类型唯一 |
| `object_links` | 对象 A、对象 B、关系（项目使用产品）、来源事项 | — |
| `item_objects` | 事项、对象 | 事项的待办和附件通过事项关联到对象 |
| `object_history` | 对象、字段、旧值、新值、依据事项和消息、确认的 `reviews` 编号 | 状态历史和参数历史都在这里 |
| `objects_fts` | 名称、别名、关键参数文本 | FTS5 `trigram` |

[02](02-技术路线.md) 第 8 节 `tags` 表中种类为「项目」「产品」的，改由 `objects` 承担；`tags` 保留客户、供应商、人员。
