## 1. 要做的事

把每天在微信里发生的工作沟通，收成一份可以检索的记录。系统用云端千问模型给每段沟通标出所属的**领域**（客户与销售、项目交付、产品研发、IT、人事等，见第 7 节），并抽出待办、需要留档的内容和决定，存到自己的服务器上。

使用人是一家十几人公司的 CEO，工作覆盖公司各个方面。分类必须一次定清、长期不改，同时数量要少，便于查找。

本系统只交付三样东西：

1. **待办清单**：从对话里抽出的下一步，每天推送，可在机器人会话里标完成。
2. **对话记录**：每段转发来的对话原文，带领域和标签，可按日期、领域、标签检索。
3. **自动存档**：值得留下的内容生成摘要文档，收到的附件按日期和领域自动归档。

系统不登录、不写入任何现有业务系统（包括 Odoo、CRM、项目管理软件、网盘）。领域名称只用来给信息归堆，不表示要写入那些系统。

## 2. 背景

日常大量工作沟通发生在微信里：客户需求、项目进度、报价、供应商、招聘、IT 问题、研发讨论、承诺的下一步、需要保存的资料。这些内容散在多个会话中，过后要靠记忆翻聊天记录，待办和文档都容易漏。

期望的结果是：沟通发生之后，服务器上出现三类东西。

1. 按领域归好类、带有客户 / 项目 / 产品等标签的记录。
2. 一份待办清单，写清谁、做什么、何时、出自哪段对话。
3. 一份文档摘要，连同原文和收到的附件放在固定目录里。

## 3. 已经核实的边界

先前的设想是：在企业微信里建一个机器人，再挂到个人微信上，从而自动拿到个人微信里的沟通。2026 年 10 月按企业微信官方文档核对后，这个设想要拆成两半。

**做得到的一半。** 企业微信可以创建「智能机器人」，并用「微信插件」让它出现在个人微信的「我的企业」里。之后在个人微信中打开这个机器人、把文字、图片、语音、文件发给它，服务器就能收到。语音由企业微信转成文字再交给服务器。机器人也可以主动把待办和每日汇总推回个人微信。这条链路是官方接口，不需要破解个人微信。

**做不到的一半。** 这个机器人读不到个人微信里和其他人已经在进行的会话。它只能收到发给机器人自己的消息。客户在普通个人微信聊天里说的话，不会自动出现在服务器上。

因此本期的收集方式是：工作沟通先在个人微信里发生，再转发或粘贴到这个机器人。全自动抓取全部个人微信会话不作为需求。若以后工作对象改为「对方用微信、本人用企业微信外部联系人」，可以另开一期，用企业微信「会话内容存档」做自动拉取。那一期需要单独开通、告知相关人，并且只能拿到开通之后、授权范围内的会话。

个人微信协议、网页版接口、在电脑客户端上模拟点击来读取他人会话，都不做。这些做法违反平台规则，也有封号风险。

### 3.1 尚未核实、第一期必须实测的事项

官方文档列出的机器人单聊可收类型是文本、图片、图文混排、语音、文件、视频，**没有写明「聊天记录」（合并转发）卡片**。下面几项只能实测确定，第一期验收时逐项记录结果：

| # | 测试 | 要记录的结果 |
| :--- | :--- | :--- |
| T1 | 个人微信多选几条消息，选「合并转发」发给机器人 | 服务器是否收到；能否拿到每条的原发送人、原时间和正文 |
| T2 | 多选后选「逐条转发」发给机器人 | 每条是否单独到达；到达间隔多长；是否带原发送人和原时间 |
| T3 | 逐条转发里夹带图片、文件 | 是否和文字一样按顺序到达 |

- T1 能拿到正文和发送人：合并转发作为首选方式，一张卡片就是一个片段（见 8.2），不需要靠时间猜。
- T1 不行：使用逐条转发，按 8.2 的规则自动合并与切分。
- T2 不带原发送人：逐条转发后，机器人看到的每条消息发送人都是本人，「谁说的」要靠模型从内容推断，推断不了就标为不确定。本人可以补一句备注说明（见 8.2）。

## 4. 使用人与成功标准

使用人是本人一人。同一时间主要在一台设备上处理结果，手机上通过个人微信看机器人的回复。

下面六条同时成立，才算前三期做成：

1. 在个人微信里把一段工作对话发给机器人后，几分钟内服务器留下原文，并给出领域和标签。
2. 连续转发的多条消息被当作一段对话处理；本人可以用一句话纠正「拆开」或「并到上一段」。
3. 其中明确的下一步变成待办；含糊的进入「待确认」，而不是直接当成已定事项。
4. 值得归档的内容生成一篇摘要，原文和附件能按日期、领域、标签找回来。
5. 每天能在个人微信里收到一份待办清单。已完成的事项不会反复出现。
6. 系统每一步的分析结果都先发给本人确认；本人提意见后按意见重做，直到本人通过才进入下一步。未经本人确认的结果不写入。

## 5. 不做什么

- 不登录、不写入现有 Odoo、CRM、项目管理软件、网盘或文档库。
- 不自动读取个人微信里未发给机器人的会话。
- 不把聊天内容同步给其他人。机器人只对本人可见。
- 不代替本人回复客户。机器人只向本人回执、提问和推送清单。
- 不在第一期处理红包、名片、视频号、投票、群接龙。这类内容只存一条「未解析」记录。

## 6. 使用场景

### 6.1 转发一段对话

客户在个人微信里谈完需求和交期。本人多选这段对话转发给机器人。服务器把这些消息合成一个片段，记下客户、事项和日期，生成待办「按约定日期回复方案」，并写一篇短摘要。机器人回复：收到几条、按几段处理、归到哪个领域、打了哪些标签、抽出了哪几条待办、哪一条还不确定。

### 6.2 直接丢给机器人

本人在机器人会话里粘贴会议要点，或发一段语音、一个文件。语音以企业微信转写的文字为准。文件保存到服务器，摘要里写清文件名和文中提到的关键数字。

### 6.3 先转发、再补一句

本人转发了一段供应商的对话，紧接着发一句「这是 A 项目的传感器备货，交期要催」。这句话并入同一片段，作为本人备注，优先用来判断领域、标签和待办。

### 6.4 纠正分段和分类

- 机器人把两件不相干的事合成了一段，本人回复「拆开」，机器人按话题重新切分后再给结果。
- 机器人把接着说的内容当成了新的一段，本人回复「并到上一段」，两段合并后重新分析。
- 机器人判断成「客户与销售」，本人回复「这是项目交付」。该片段改领域，已生成的待办跟着改，不另起一条重复待办。

### 6.5 每天看清单

每个工作日固定时间，机器人在个人微信里推送：未完成待办（按领域分组）、当天新增摘要、仍待确认的条目。本人回复「完成 3」这类短句后，对应待办标为完成。

## 7. 信息怎么分类

每个片段从两个方面标注，另外抽出标签。

### 7.1 领域（必选一个主领域，可加一个次领域）

按「这件事最后归公司哪一块负责」来判断。一件事同时涉及两块时，归到最终负责交付结果的那一块作为主领域，另一块作为次领域。

| 领域 | 放什么 | 至少抽出的字段 |
| :--- | :--- | :--- |
| 客户与销售 | 商机、客户需求、报价、合同、回款、客户关系维护、投诉 | 客户或公司、联系人、事项、金额或报价、阶段、下一步 |
| 项目交付与售后 | 给客户做的项目：进度、交付、安装调试、验收、售后问题 | 项目名、客户、事项、责任人、日期、状态 |
| 产品研发 | 自有产品的规划、需求、设计、开发、测试、技术方案、参数 | 产品名、事项、关键参数、责任人、日期 |
| 采购与生产 | 供应商、询价、采购、物料、库存、生产外协、物流 | 供应商、物料或料号、数量、价格、交期 |
| 财务与法务 | 发票、付款、报销、税务、银行、融资、法律事务 | 对方、金额、日期、事项 |
| 人事行政 | 招聘、入离职、员工事务、薪酬考勤、培训、办公行政 | 人员或岗位、事项、日期 |
| IT 与信息化 | 服务器、网络、账号权限、软件订阅、信息安全、Odoo 等内部系统本身 | 系统或设备、事项、责任人、日期 |
| 其他 | 闲聊、表情、与工作无关、暂时归不了类的内容 | 只留原文 |

公司战略、投资人、对外合作等少量事务，按其具体内容归入上表（如融资归财务与法务，合作开发归产品研发）。确有大量无法归入的内容，评估后再增加领域，不在使用中随手加类。

### 7.2 类型（可多选）

| 类型 | 含义 |
| :--- | :--- |
| 待办 | 需要本人或某人下一步去做的事：做什么、谁做、何时、出自哪段对话 |
| 记录 | 值得留档的纪要、参数、资料、附件说明，生成文档 |
| 决定 | 已经拍板的事项（价格定了、方案选定、人员确定），单独标出便于以后查 |
| 待确认 | 置信度不足，或原文里没有明确的人、事、时间。不进正式待办，在清单里单列 |

### 7.3 标签

客户名、供应商名、人名从内容中抽出，作为标签保存。项目和产品不只是标签，而是清单里的对象（见 8.8）。查找某个客户、项目或产品的全部内容靠标签和对象，不为单个客户或项目新开分类目录。

同一对象的不同写法（如简称和全称）归并为同一标签或对象；不能确定是否同一对象时，在确认时由本人决定一次，之后记住。

**领域与清单的关系。**

领域回答「这件事归公司哪一块负责」，项目和产品清单回答「这件事关于哪个项目、哪个产品」。两者独立，交叉使用：可以查「某项目在采购方面的事」「某产品在研发和售后两边的记录」。

### 7.4 通用规则

- 一个片段如果包含几件不相干的事，切成几条，每条单独标领域、类型和标签（见 8.2）。
- 模型必须给出置信度。置信度不足时进入「待确认」。
- 金额、日期、料号、阈值、端口这类关键参数，摘要里保留原话中的值。模型没有看到的数字不允许补写。

## 8. 功能要求

### 8.1 收集

- 个人微信里可以找到并打开这个机器人。
- 支持文本、图片、语音转写文本、文件；合并转发的聊天记录按第 3.1 节实测结果决定是否支持。群里只有 @机器人 的内容才会进来；第一期以单聊为主。
- 同一条消息重复推送时只处理一次。
- 收到后不对每条单独回复。片段收齐后按第 8.7 节逐步发给本人确认，全部确认后回复一句写入结果。分析失败时在确认消息里说明原因，原文仍保留。

### 8.2 片段：逐条转发时的自动合并与切分

企业微信本身不会告诉服务器「这几条是一次转发的」。合并与切分由服务器按下面三层规则完成。

**第一层：按时间合并成片段（自动）。**

- 多选逐条转发时，消息会在很短时间内连续到达。服务器收到一条消息后开始计时，在「静默时间」内又收到新消息就并入同一片段并重新计时；超过静默时间没有新消息，片段收齐，开始分析。
- 静默时间默认 60 秒，做成可配置项，按第 3.1 节 T2 实测的到达间隔调整。
- 片段收齐后才调用模型，不对单条消息逐条分析。
- 合并转发卡片（若 T1 可用）直接作为一个片段，不走计时。

**第二层：本人显式指令（可选，优先于自动规则）。**

| 指令 | 作用 |
| :--- | :--- |
| 发送「好了」或「完」 | 立即结束当前片段，不等静默时间 |
| 片段收齐前后紧跟一句普通说明（如「这是 A 项目的」） | 在静默时间内到达的说明并入片段，作为本人备注，判断时优先采信 |
| 「拆开」 | 对上一片段重新按话题切分 |
| 「并到上一段」 | 把最近一个片段并入它之前的片段，重新分析 |

本人不发任何指令时，系统只靠第一层和第三层也要能正常工作。

**第三层：按话题切分与关联（模型完成）。**

- 一个片段里如果有几件不相干的事（例如前半段谈报价、后半段谈招聘），模型把它切成几条，每条单独标领域、类型和标签。
- 模型判断新片段与最近已处理片段属于同一件事（同一客户、同一项目、话题延续）时，不改动原片段，而是通过相同标签关联起来；把握不大时在回执里提示「看起来和上一段是同一件事，需要合并吗」。
- 切分和关联的结果都写进回执，本人可以用第二层指令纠正。

### 8.3 分析

- 调用阿里云百炼的 `qwen3.8-max`。密钥只放在服务器环境变量里。
- 输入是整个片段（按到达顺序排列），以及同一会话里最近几个已确认片段的摘要和标签，避免把「好的」单独分成一类。
- 已知的标签清单（客户、项目、产品、供应商）一并提供给模型，优先匹配已有标签。
- 输出固定结构：切分后的条目；每条的主领域、次领域、类型、标签、抽取字段、待办草稿、文档摘要、置信度、不确定的原因。
- 模型超时或返回无法解析时，片段标为「分析失败」，可稍后重试，不丢失原文。

### 8.4 待办

- 每条待办有标题、负责人（原文没写则默认本人）、截止时间（原文没写则为空）、来源片段、领域、标签、状态。
- 状态只有：待确认、未完成、已完成、已忽略。
- 同一来源不要生成两条意思相同的待办。
- 本人用机器人会话把待办标成完成或忽略。

### 8.5 对话记录与自动存档

- **完整保存**：机器人会话里的每一条消息都保存，包括本人发来的文字、图片、文档、语音、视频，以及机器人发出的回执、提问、清单和本人的作答。附件保存原文件，收到即存，在分析之前完成；分析失败不影响保存。每天有一份按时间排列的当日完整对话记录。
- **对话记录**：每个事项的原文按到达顺序保存，带收到时间、领域、标签、本人备注，附件在出现位置给出链接。闲聊（领域为「其他」）也保存原文，只是不生成待办和摘要。
- **摘要文档**：类型含「记录」的条目生成一篇摘要文档，包含标题、领域、标签、摘要、原文摘录、来源片段和附件清单。
- **附件分类归档**：图片、文档、语音、视频跟着所在的事项归档，在事项文件夹里按种类分开放置，文件名保留原名，重名时加序号，不覆盖。文档和图片里能提取的文字一并保存，可以被检索。
- 存档目录按「日期 / 领域 / 事项」组织，不依赖数据库也能直接浏览。改领域、拆开、合并后，存档跟着调整。
- 只保存机器人实际收到的内容和附件，不从个人微信其他会话里取文件。
- 可以在机器人会话里用短指令查找，例如「查 某某科技」列出该标签最近的记录和待办；结果只返回标题和日期，详情到服务器上看。

### 8.6 每日清单

- 工作日推送一次。时间在实施时做成可配置项，默认工作日 18:00（北京时间）。
- 内容顺序：未完成待办（按领域分组，过期的排前）、今日新增存档、今日记录的决定、待确认条目。
- 当天没有新内容时仍推送，并写明「今天没有新的待办」。

### 8.7 逐步确认

- 系统处理一段内容时分几步：理解与切分、与以前内容的关联、分类、待办与摘要、写入计划。每一步的结果先发到个人微信，本人确认后才进入下一步。
- 本人可以回复：「通过」；修改意见（例如「第一件是项目交付」「面试那件不用记」）；「全部通过」（这一段后面的步骤不再逐一确认）；「放弃」（这一段不整理，原文仍保存）。
- 本人提了修改意见，系统按意见重新做这一步，再发给本人确认，直到本人通过。意见针对的是更早的步骤时，回到那一步重做，之后的步骤重新确认。
- 一次只发一条待确认的消息，前一条处理完再发下一条，避免回复对不上。
- 未经本人确认的分析结果不写入待办、记录和存档。原文和附件在收到时就保存，不受确认影响。
- 本人直接下达的指令（完成、忽略、查找、撤销等）直接执行，不再确认。
- 每一步是否需要确认可以在配置里单独关闭，默认全部需要确认。

### 8.8 自动维护的清单

- 系统维护三份清单：**项目清单**、**产品清单**、**文件夹结构清单**。
- 项目有客户、状态（商机 / 实施中 / 交付验收 / 售后 / 暂停 / 已结束）、负责人、关键日期、涉及的产品，可以分子项目或阶段。产品分产品线、产品、型号或版本，有状态（规划 / 研发 / 试产 / 在售 / 停产）和关键参数，参数变化保留历史。
- 每条记录、待办和附件都关联到相关的项目和产品。可以从项目看到它的子项目、涉及的产品、全部记录、待办和文件；也可以从产品看到用了它的项目。
- 新项目、新产品、状态变化、参数变化、关联关系由系统从对话中提出，经本人逐步确认后才写入。最近动态、待办数、文件数等由系统自动统计。
- 文件在存档里只存一份，清单和每个项目、产品的页面用链接指向它们，不复制文件。清单文件放在存档目录的「清单」下，不打开数据库也能浏览。
- 文件夹结构清单列出存档目录的层级和每层的事项数、文件数。
- 本人可以在机器人会话里纠正：改关联、改上级、改状态、合并重复的项目或产品。可以发「项目清单」「产品清单」「查 某项目」查看。
- 客户、供应商、人员第一版仍按标签处理，不建清单。

### 8.9 用好历史

- 整理新内容和回答提问时，都要结合全部历史：以前的对话、附件、记录、待办、项目和产品。不能只看当前这一段。
- 新内容和以前的记录是重复、补充、修订、进入下一阶段还是互相矛盾，系统在「关联」这一步列出，本人确认。修订时保留旧的说法和修改日期；矛盾时列出双方原话，由本人决定以哪个为准，没决定之前在每日清单里提醒。
- 回答问题默认用最新有效的说法；问到变化过程时按时间线回答；有没定的矛盾必须说出来。
- 回答里的每个说法都注明来自哪条记录、哪条消息或附件第几页。查不到就说查不到，不编造。
- 回答较长的整理（汇总、对比）可以写成文件发给本人。

## 9. 隐私与保留

聊天内容只放在自己的服务器和百炼的当次调用中。不写入公开仓库，不写进 Git，不同步到其他系统。日志里可以有消息编号和处理状态，不记录全文和密钥。

原文、摘要、附件默认保留，直到本人删除。删除后服务器上的对应文件和数据库记录一并去掉。

## 10. 分期

| 期 | 使用人能感知到的结果 |
| :--- | :--- |
| 第一期 | 个人微信发给机器人，服务器收到并保存原文；按静默时间合成片段并回复「已收到 N 条」；完成第 3.1 节 T1–T3 实测 |
| 第二期 | 文本片段按领域、类型、标签分类并按话题切分；生成待办和摘要存档；每日清单推送；可回复完成、改领域、拆开、并到上一段、查找 |
| 第三期 | 图片、文件、语音转写进入同一条流水线，附件自动存档 |
| 以后另议 | 把待办和存档写入 Odoo 19 等业务系统；工作沟通改走企业微信外部联系人后，用会话内容存档自动拉取。均不在前三期之内，开始前需先修改本文档 |

## 11. 验收

第一期到第三期都做完时，用下面几条验收。

1. 多选 8 条消息逐条转发，服务器合成 1 个片段，机器人只回复一次「已收到 8 条」，8 条原文都在对话记录里。
2. 转发一段对话后 10 秒内补一句说明，说明并入同一片段并影响分类结果。
3. 一次转发里前半段谈报价、后半段谈招聘，结果切成两条，分别归入客户与销售、人事行政。
4. 回复「拆开」「并到上一段」后，分段结果随之改变，待办不重复。
5. 转发一段含客户名、日期和下一步的文字，正式待办里出现这一步，存档里有摘要，领域和客户标签正确。
6. 转发 IT、研发、采购、人事、财务各一段样例，各自归入正确领域。
7. 转发一段闲聊，原文有记录，但不产生待办和摘要。
8. 转发一段意图不清的话，只出现在待确认。
9. 把同一段话再发一次，待办和存档不重复。
10. 回复改领域、完成后，清单状态随之变化。
11. 发一个文件，服务器存档目录里能按日期和领域找到原文件，摘要不编造文件里不存在的数字。
12. 回复「查 某客户」，能列出该客户最近的记录和待办。
13. 到点后个人微信收到当日清单，待办按领域分组。
14. 仓库和工作区里搜不到 API 密钥和机器人 Secret。
15. 第 3.1 节 T1–T3 的实测结果已记录，并据此确定了首选转发方式和静默时间。
16. 转发一段提到新项目和某产品的对话，确认后项目清单里出现该项目，关联到客户和产品；产品页面里能看到这个项目。
17. 转发一段「某项目验收通过」的对话，确认后该项目状态变为售后，状态历史里有出处。
18. 打开存档目录下的「清单」，从项目清单点到项目页，再点到事项文件夹里的原文件，全程不需要数据库。
19. 先转发「交期 11 月 5 日」，几天后转发「交期改到 6 号」：关联这一步列为修订；之后问「交期是哪天」，回答 11 月 6 日，并说明原来是 5 日、哪天改的。
20. 两段对话里数量说法不一致：关联这一步列出双方原话；本人未裁决前，问到数量时回答里提到这个冲突。
21. 问一个答案只在某个附件内页里的问题，回答正确并注明附件和页码；问一件从没记录过的事，回答查不到。

## 12. 默认决定

下面这些先按此执行。若与实际情况不符，改文档后再做。

- 收集通道用企业微信智能机器人的长连接，加上微信插件，出现在个人微信里。
- 企业若不允许成员创建 API 模式机器人，就另注册一个仅供本人使用的企业微信，不使用公司组织里的客户数据。
- 模型用百炼北京地域的 `qwen3.8-max`。需要固定行为时改用带日期的快照 `qwen3.8-max-0902`。
- 领域固定为第 7.1 节的七个加「其他」，使用中不随手增加。
- 逐条转发的片段静默时间默认 60 秒，按实测调整。
- 结果只存在自己的服务器：阿里云 ECS `firematrix`（见 [03-部署实施.md](03-部署实施.md)），不对接 Odoo 或其他业务系统；代码放 GitHub，数据不进 Git。
- 所有输入都来自本人发给机器人的内容。
