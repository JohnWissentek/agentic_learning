# 智能体工作流调试档案与避坑方法论（`debug_records/`）

> **本目录的「双视角编写约定」（以后每新增一份调试档案都必须严格遵守）**：  
> 本目录的每一份文档同时服务两位读者——**没有编程背景的董事长**，以及**将来接手改代码的 AI Coding 智能体**。  
> 因此每个知识点、每起故障、每条规范都强制拆成两段并行书写：
> - **🗣️ 通俗白话解读（给您看）**：不用程序黑话，用日常“老板—秘书—审计—档案室”的办公逻辑讲清因果，意思准确、逻辑严密、一眼看懂；
> - **🤖 工程技术规格（给 AI Coding 看）**：写清精确的文件路径、函数名、字段名、数据流约束与验收条件，将来把文档直接喂给 AI 智能体就能精准改码防踩坑。

## 一、先讲透一个核心真相：为什么 AI 经常“看似变傻”，其实 80% 不怪大模型？

### 🗣️ 通俗白话解读
把您现在这套 AI 助手想象成一间**三个人配合的小办公室**：
1. **传话跑腿员（编排代码）**：负责收您的微信、翻日历、查通讯录、把纸条递给写方案的人，再把写好的方案递给复核员。
2. **写方案的秘书（主推大模型）**：负责看懂您的话，把事情整理成规范的任务卡。
3. **把关的审核员（审计规则 + 审计大模型）**：负责检查秘书有没有瞎编数字、有没有把抄送的活硬派给老板。

当您觉得“AI 怎么这么笨，我明明说了本周五，它还说我没给”时，**十有八九不是秘书笨，而是中间那个“传话跑腿员”干了糊涂事**——比如跑腿员只把旧草稿递给了审核员，忘了把您刚发的新纸条递过去；审核员一看草稿里没写本周五，就骂秘书“你敢瞎编日期”，逼着秘书把好不容易算对的本周五又给擦掉了！

### 🤖 工程技术规格（三层归因诊断模型）

| 归因层级 | 工程定义 | 典型故障特征 | 根治手段 |
| :---: | :--- | :--- | :--- |
| **L1｜硬编码与编排层（Orchestration & Guardrails）** | Python 状态机、节点间 `WorkflowState` 传参、确定性正则/规则函数、DB 读写与记忆持久化逻辑 | 状态字段漏传/被覆盖；硬校验规则过死误杀合法推理；跨通道护栏未加通道锁；脏数据写入 `conversation_turns` | 必须修改 Python 源码与确定性护栏；单纯更换更强 LLM 或改 Prompt **无法根治** |
| **L2｜上下文与提示词层（Context & Presentation）** | 注入给模型的系统事实（如日历锚点）、System Prompt 边界定义、以及内部反思文本与用户展示文本的隔离 | 缺少确定性外部事实（如本周/下周日期映射）；内部反思术语/字段名泄露至用户可见字段；摘要与结构化卡片内容重复 | 补齐确定性事实注入；在 Prompt 与渲染层做“内部状态 vs 用户展示”物理隔离 |
| **L3｜大语言模型固有边界（LLM Capability Boundary）** | 无确定性工具/代码兜底时，Transformer 自回归推理的固有短板 | 跨周心算星期几偏差 1 天；逐字符抄写 100+ 字节 Base64 `conversationId` 漏字；长 Prompt 多约束并发时偶发遗忘单条规则 | 凡涉及精确日期计算、长 ID 绑定、权限与角色判定，全部下沉为 Python 确定性代码或短引用映射 |

## 二、以后再做智能体工作流，必须守住的 8 条避坑铁律（白话 + 技术双版）

### 铁律 1：日历、数字、长编号，永远不要考大模型“心算和默写”
- **🗣️ 白话版**：别让秘书靠脑子推算“昨天是几号、下周三是几号”，也别让她手抄一串 100 位的乱码邮件编号。开工前先把印好的《本周/下周日历对照表》贴在秘书和审核员桌上，长编号统一用“1号信、2号信”代替，最后由系统自动换回真编号。
- **🤖 技术版**：每次调用 `producer` 与 `critic` 前，由 Python 确定性函数生成 `昨天 / 今天(周几) / 明天 / 本周一~周日 / 下周一~周日` 日历锚点表并注入共享上下文；外部长 ID（如 Graph `conversationId`）采用短占位符 `MAIL-k` 并在代码层做确定性回填（`_backfill_mail_conversation_ids`）。

### 铁律 2：多角色接力审核时，每个人拿到的“老板原话”必须一模一样
- **🗣️ 白话版**：如果工作流里有“秘书写草稿 → 审核员把关”两道岗，您后来补充的任何一句修改意见，必须**同时复印两份**，秘书一份、审核员一份。只要漏给审核员，审核员就会把您新提的要求当成秘书胡编的，直接一笔划掉。
- **🤖 技术版**：在 `LangGraph` 状态机中（尤其 `revise_pending` 等状态覆写分支），`user_correction` 与用户最新原文必须作为一等字段同时传入 `_node_producer_drafter`、`deterministic_critic_check` 与 `_node_heterogeneous_critic`，严禁覆写 `raw_text` 导致下游审计节点上下文失明。

### 铁律 3：防幻觉规则要“防真造假”，别把“看日历算出来的日期”当造假打死
- **🗣️ 白话版**：设审核员是为了防止 AI 瞎编价格、瞎编合同页码；但您说“昨天开始联系”，秘书看日历写成“11月24日”，这是天经地义的正常换算。如果审核员死板地拿着放大镜说“老板原话里没出现‘24’这两个数字，算你造假！”，就会把正确的日期硬改错，还白白折腾两轮浪费几十秒。
- **🤖 技术版**：`deterministic_critic_check` 的数值保真白名单（`combined_source`）必须包含确定性日历锚点表中的所有合法日期；数字保真审计应聚焦金额、参数、型号、页码与比例，避免误杀合法相对日期推算触发无效 `max_reflection_loops` 重试。

### 铁律 4：不同渠道的规矩必须“挂牌分区”，不能拿管邮件的规矩去管微信
- **🗣️ 白话版**：邮件里有“抄送（Cc）”，别人发邮件顺手抄送您，您只是知情旁观，不是干活的人；但您在微信里亲自交代“让杨丽丽去联系电厂”，您就是发号施令的负责人，杨丽丽是执行人。绝不能把“邮件抄送不管事”的规矩错用到微信交办上。
- **🤖 技术版**：通道专属护栏必须绑定显式通道判定（如仅当 `[SYSTEM_TRUSTED_MAIL_META]` 存在且 `chairman_role=cc_observer` 时触发 `cc_observer` 防错派拦截）；微信通道（`source_channel="wechat"`）交办默认 `chairman_role="owner"`、`owner="徐宏玮"`、`assignee=<执行同事>`。

### 铁律 5：“厨房里的吵架记录”绝不能端到老板的餐桌上
- **🗣️ 白话版**：秘书写错被审核员打回重写，这是后厨内部的自我纠错。端给您看的任务卡，只需要干净利落地列出“谁干、干什么、什么时候交”，绝不该把“根据审计打回整改要求，我把某某字段改回空字符串”这种内部过程废话、英文代码词塞进您的卡片和备注里；同时卡片下面 1～5 条已经写清的事，顶部就别再用一大段话重复念一遍。
- **🤖 技术版**：① Prompt 严禁将反思原因、Schema 字段名（如 `planned_end_at`、`missing_required_fields`、`cc_observer`）或工具名写入用户可见字段（`executive_summary`、`comments`、`timeline`）；② 渲染层（`format_decision_card`）对单任务卡省略冗余长摘要，并过滤 `citations` 中的系统噪点，仅保留真实文档页码/邮件原件引用。

### 铁律 6：外部收进来的长材料，别当成“老板亲口说的话”塞进聊天记忆
- **🗣️ 白话版**：系统每小时自动拉进来的几千字外部邮件，属于“资料档案”，不是您在微信里亲口说的话。如果把它当成您的发言记进聊天记录，半小时后您在微信聊一件毫不相干的新事，AI 一翻聊天记录全是刚才那封邮件，立刻就会串味跑偏。
- **🤖 技术版**：`conversation_turns` 仅持久化真实用户输入与精炼后的系统卡片回执；`sender.startswith("mail:")` 触发的批量原始 `[UNTRUSTED_EXTERNAL_DATA]` 文本不得写入 `user` 角色对话历史，外部原文统一归档于 `raw_sources` 按需检索。

### 铁律 7：系统自己算出的硬结论，必须和外部不可信原文“物理分框”
- **🗣️ 白话版**：外部客户发来的邮件内容是不可信的（里面可能夹带乱七八糟的指令甚至钓鱼话术），系统自己根据邮箱地址算出来的“谁发给谁、谁只是抄送”是可信事实。两者必须分开放，不能混在同一个框里，否则外部邮件正文写一句假指令就能骗过 AI。
- **🤖 技术版**：可信元数据统一置于 `[SYSTEM_TRUSTED_MAIL_META]...[/SYSTEM_TRUSTED_MAIL_META]` 外部块，仅将邮件主题与正文包裹于 `[UNTRUSTED_EXTERNAL_DATA]...[/UNTRUSTED_EXTERNAL_DATA]`；下游规则与回填函数严格只解析可信块。

### 铁律 8：每踩一次真机怪现象，就把真实原话变成一条“永久安检用例”
- **🗣️ 白话版**：改完一个毛病，千万别只靠“看着顺眼了”就收工。把您今天发过的那两句真实原话永久存进自动化体检表里，以后不管怎么升级模型、怎么改代码，每次上线前自动跑一遍，保证踩过的坑一辈子不再踩第二次。
- **🤖 技术版**：遵循防串谋 TDD 闭环，将每次线上真实故障的完整多轮输入固化为黑盒回归用例（`tests/unit/`）并跑通 Red → Green 全量验证后方可发布。
