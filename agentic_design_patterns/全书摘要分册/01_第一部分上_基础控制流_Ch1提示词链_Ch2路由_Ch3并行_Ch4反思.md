## 第 1 章：提示词链（Prompt Chaining / Pipeline Pattern，PDF P23–P35）

- **核心概念**：采用“分而治之（Divide-and-Conquer）”策略，将复杂的单体任务拆解为线性序列的子任务。前一个提示词的输出作为后一个提示词的输入，构建确定性的依赖链条。
- **解决的核心痛点**：克服单一复杂提示词带来的指令忽略（Instruction Neglect）、上下文漂移（Contextual Drift）、错误传播放大以及高认知负荷引发的幻觉（Hallucination）。
- **关键工程机制**：
  - **结构化输出（Structured Output）**：步骤间的数据传递必须严密，通常强制要求输出 JSON 或 XML 格式（如配合 Pydantic Schema），确保机器可读性与解析确定性，并在步骤间插入确定性校验代码或外部工具调用。
  - **上下文工程（Context Engineering，PDF P32–P34, Fig. 2）**：超越传统的提示词措辞优化，是在 Token 生成前为模型构建完整信息环境的系统学科。它整合了系统提示词（System Prompt）、外部检索文档（RAG）、工具实时输出（Tool Outputs）以及隐式数据（用户身份、历史状态、环境参数），决定了智能体态势感知的上限。
- **七大核心工程应用场景（7 Practical Use Cases，PDF P25–P28）**：
  1. **信息处理管道（Information Processing Pipelines）**：如“提取文本 -> 总结摘要 -> 提取实体 -> 检索数据库 -> 生成报告”。
  2. **复杂查询分解解答（Complex Query Answering）**：**在固定流水线的第 1 步利用 LLM 将复杂多跳问题拆解为若干独立子问题**，后续步骤依次求解并汇总（即“宏观链条由架构师预设、微观子问题由首步节点动态拆解”的混合模式）。
  3. **数据提取与转换（Data Extraction and Transformation）**：通过多轮提取、清洗校验与外部知识库匹配，将非结构化发票/表单转为规范 JSON。
  4. **含审校的内容生成（Content Generation Workflows）**：拆解为“选题构思 -> 大纲生成 -> 分段扩写 -> 审校润色”。
  5. **带状态的对话智能体（Conversational Agents with State）**：每轮对话按“提取意图与实体 -> 更新对话状态 -> 生成回复”顺序流转。
  6. **多步代码生成与精炼（Code Generation and Refinement）**：拆解为“理解需求生成伪代码 -> 编写初版代码 -> 静态检查/补齐测试 -> 文档注释生成”。
  7. **多模态与多步推理（Multimodal and Multi-step Reasoning）**：依次拆解图文识别、标签提取与表格规则解释。
- **适用法则**：当任务对单一提示词过于复杂、包含多个独立的处理阶段，或需要在步骤之间穿插外部工具调用与确定性数据转换时使用。

## 第 2 章：路由（Routing，PDF P36–P49）

- **核心概念**：在智能体工作流中引入条件逻辑（Conditional Logic）与动态仲裁机制。智能体不再遵循固定的线性执行路径，而是先评估输入意图、环境状态或前序步骤结果，动态地将控制流分发至最匹配的专用工具、子链或子智能体。
- **路由在运行周期中的三大介入位置（Multiple Junctures，PDF P37）**：
  1. **入口分诊（At the Outset）**：作为工作流第一站，对初始用户请求做意图分类与首站分流。
  2. **处理链中间节点（At Intermediate Points）**：在多步链路中间，根据上一步执行结果（如置信度高低、校验是否通过、风险等级）动态决定下一步分支。
  3. **子程序或工具选择（During a Subroutine）**：在特定节点内部从工具池中按需挑选最匹配的单个工具。
- **四种核心路由实现机制（PDF P38–P39）**：
  1. **基于 LLM 的路由（LLM-based Routing）**：通过提示词让生成式模型分析输入并仅输出分类标识符（如 `'Order Status'`、`'Technical Support'`），由外层框架读取标识符并跳转分支。
  2. **基于嵌入的路由（Embedding-based Routing / Semantic Routing）**：将输入查询转化为向量嵌入，与预设路由能力的向量进行语义相似度比对，路由至距离最近的分支，适用于基于语义而非关键词的高速分发。
  3. **基于规则的路由（Rule-based Routing）**：使用传统的 `if-else`、`switch`、正则表达式或结构化字段提取进行确定性分发，速度极快（亚毫秒级）且零成本，但灵活性较低。
  4. **基于传统机器学习模型的路由（ML Model-Based Routing）**：使用标注数据专门微调一个轻量级判别式分类器（Classifier），将路由逻辑编码在模型权重中，推理解析时不依赖生成式提示词，兼顾低延迟与高准确率。
- **三大主流框架的路由架构差异（PDF P40–P48）**：
  - **LangChain LCEL（`RunnableBranch`）**：主要用于根据上一步单次输出做无状态的树状条件分支跳转。
  - **LangGraph（基于全局累积状态 `Accumulated State` 的条件边 `add_conditional_edges`）**：路由决策不仅看最后一步输出，而是综合考量整个图运行至今累积的全局状态（如历史重试次数、多节点评分、用户画像）进行动态流转。
  - **Google ADK（`Auto-Flow` 自动委派机制）**：父协调器通过 `sub_agents` 挂载子智能体并读取其 `description`，由底层运行时自动将请求委派给最匹配的子智能体，无需手写显式分支判断代码。
- **适用法则**：当系统需要对多样化的输入进行分诊（Triage）、意图分类，并在多个截然不同的工作流、工具或专家子智能体之间做出选择时使用。

## 第 3 章：并行化（Parallelization，PDF P50–P64）

- **核心概念**：识别工作流中相互之间无直接数据依赖的子任务（如多个 LLM 调用、多源 API 请求或多个独立子智能体），并同时并发执行它们，最后在汇聚节点（Merger/Synthesis Node）整合结果。
- **关键技术辨析与修正**：
  - **并发（Concurrency）与并行（Parallelism，PDF P53）**：在 Python 等环境中，利用 `asyncio` 事件循环在单线程内趁网络 I/O 等待（如等待大模型 API 或外部接口响应）时智能切换任务属于**并发**；而跨多核或多机的同时计算属于**并行**。在以 I/O 密集型为主的智能体系统中，异步并发能极大掩盖外部服务延迟。
  - **三大框架中的扇出与扇入原语区分（Fan-out / Fan-in，PDF P51–P62）**：
    - **LangChain LCEL**：使用 **`RunnableParallel`**（或字典字面量）将同一个输入同时喂给多条无状态子链，并打包为字典传入下一步合成提示词。
    - **LangGraph**：**不依赖 `RunnableParallel`**，而是通过 **图拓扑的多分支边（同一节点连向多个并行节点）+ 状态归约器（State Reducers，如 `Annotated[list, operator.add]` 防止并发覆写冲突）** 或动态 **`Send` API（Map-Reduce 动态扇出）** 实现有状态并发。
    - **Google ADK**：使用 **`ParallelAgent`** 并发运行多个子智能体（各自通过独立 `output_key` 写入 `session.state`），外层再嵌套一个 **`SequentialAgent`** 串接下游的 **`MergerAgent`** 进行汇总。
  - **汇聚节点的“严格闭卷防幻觉铁律”（Strict Grounding in MergerAgent，PDF P60–P62）**：汇聚合成节点的系统提示词必须强制规定 **“仅基于上游并行分支提供的输入摘要进行综合，严禁补充任何外部背景知识或臆测”**，以防汇总模型在整合多方观点时自行脑补。
  - **工程代价（Trade-offs，PDF P63）**：并发与并行显著增加了架构设计、状态同步、局部报错隔离以及交错日志追踪（Debugging & Tracing）的工程复杂度。
- **适用法则**：当工作流包含多个互不依赖的外部 I/O 查询（如同时查新闻、股价、财报）、对同一数据的多维度分析（如同时做情感分析、关键词提取、合规检查），或并行生成多个候选方案以供择优（A/B 测试或投票）时使用。
- **专项深读**：[05_Chapter3_Parallelization_高亮解析_适用与禁区场景及LangGraph实现指南.md](../05_Chapter3_Parallelization_高亮解析_适用与禁区场景及LangGraph实现指南.md)

## 第 4 章：反思（Reflection，PDF P65–P78）

- **核心概念**：在智能体工作流中引入反馈闭环（Feedback Loop）与元认知（Meta-cognition）机制。智能体不再将初次生成的结果直接作为最终输出，而是对自身的输出、内部状态或推理过程进行评估，识别缺陷并迭代修正，直至满足停止条件（达到质量标准或达到最大迭代次数）。
- **两种架构实现模式（PDF P66–P67, Fig. 1 & Fig. 2）**：
  1. **自我反思（Self-Reflection）**：由同一个智能体通过多轮提示词对自身生成的内容进行检查和重写。
  2. **生产者-批评者模型（Producer-Critic / Generator-Reviewer Model）**：将职责解耦为两个独立的逻辑角色——**生产者智能体（Producer）** 专注于执行初始任务和重构内容；**批评者智能体（Critic）** 被赋予截然不同的系统人设（如“苛刻的高级软件工程师”或“严谨的事实核查员”），专门依据预设标准寻找漏洞并提供结构化修改意见（在 Google ADK 中常通过 **`LoopAgent`** 包裹 Generator 与 Reviewer 并检查 `session.state` 中的状态标签实现循环退出）。这种关注点分离有效消除了单一模型审查自身工作时的“认知偏见（Cognitive Bias）”。
- **跨模式协同机制（PDF P67、P73）**：
  - **与第 11 章《目标设定与监控》协同**：目标设定提供衡量成败的终极标尺（Target Checklist），而反思模式则充当具体的**纠偏执行引擎（Corrective Engine）**。
  - **与第 8 章《记忆管理》协同**：没有会话记忆的反思是孤立且健忘的；结合记忆管理后，智能体才能记住上一轮批评指出的错误，避免在多轮重构中“改了东墙塌了西墙”或重复犯错。
- **工程权衡（Trade-offs，PDF P77）**：反思模式以牺牲延迟（Latency）和计算成本（Token 消耗）为代价换取高质量输出；且随着迭代轮次增加，对话历史迅速膨胀，容易逼近上下文窗口上限或陷入死循环。
- **适用法则**：当最终输出的质量、准确性和复杂约束遵循度远比响应速度和成本更重要时使用（如长文撰写、代码生成与调试、复杂规划验证）。
