# LangGraph 与状态机架构图制图规范：严格遵循 UML 2.5 状态机图标准

凡在本工作区绘制、生成、修改或评审 **LangGraph 状态图（`StateGraph`）、智能体状态机架构图、多阶段受控状态流转图**（无论使用 Draw.io `.drawio`、Mermaid、PlantUML、SVG 还是文档插图），**必须严格遵循 OMG UML 2.5 状态机图（Behavioral State Machine Diagram）规范**，严禁使用普通流程图（Flowchart）或非标自造图元混搭代替。

详细映射表与 Draw.io / Mermaid 标准样式激活 `uml25-state-machine-diagram` 技能查阅。

---

## 1. UML 2.5 图元硬约束（禁止混用流程图符号）

1. **初始伪状态（Initial Pseudostate `●`）**：
   - 必须使用**实心黑圆**表示状态机或复合状态的唯一入口（对应 LangGraph `START`）；无入边，唯一出边指向首个状态，出边上**不得标注触发事件或 `[guard]`**（仅允许标注 `/ 初始化动作`）。
2. **终止状态（Final State `◉`）**：
   - 必须使用**牛眼双圆（实心黑圆外包同心圆环）**表示本轮状态机生命周期终结（对应 LangGraph `END`）；只有入边，严禁引出任何出边。
3. **状态节点（Simple / Composite State）**：
   - 一律使用**圆角矩形（Rounded Rectangle）**；**严禁在状态机图中混入平行四边形（I/O）、圆柱体（数据库）或直角矩形（流程图步骤）充当状态节点**（外部存储读写与消息收发应作为状态内部的 `entry / do / exit` 动作或迁移上的 `/ effect` 表达）。
   - 内部隔间（Compartments）按 UML 2.5 标准书写：`entry / <进入时确定性动作>`、`do / <状态内活动或模型调用>`、`exit / <退出动作>`。
   - **复合状态（Composite State）与正交并发区域（Orthogonal Regions）**：大阶段分区使用带顶部标题栏的复合状态圆角大框；独立运行的定时任务、心跳监控等并发伴随机制，使用虚线分隔的**正交区域（Orthogonal Region）**绘制，不得与主状态流混连乱线。
4. **选择伪状态（Choice Pseudostate `◇`）**：
   - 动态条件路由（对应 LangGraph `add_conditional_edges`）必须使用**空心小菱形 `◇`**（评估前序动作执行后的实时状态属性）；
   - 从 `◇` 引出的所有分支**必须具备互斥且完备的方括号监护条件 `[guard]`，且必须包含一条显式 `[else]` 兜底分支**，从图面上杜绝状态悬空或死锁。

---

## 2. 迁移语法（Transition Syntax）与有界循环证明

1. **标准三段式迁移标签**：每条有向实线迁移必须严格遵循格式：
   `触发事件 [监护条件] / 产生的动作或副作用`
   - 方括号 `[...]` **仅限**书写布尔判断条件（Guard）；
   - 斜杠 `/ ...` **仅限**书写迁移瞬间执行的确定性效果（Effect，如发消息、写库、计数 `+1`）。
2. **回环必须自证有界（Bounded Loop Proof）**：
   - 任何回退或自循环边必须在 `[guard]` 中显式写出循环计数器上限（如 `[审核未通过 且 重写次数 < 2] / 重写次数+1`），并配套画出达到上限时的逃生迁移（如 `[审核通过 或 重写次数 >= 2]`），直观证明绝无死循环。
3. **等待外部事件状态（Wait / Idle State）**：
   - 像“生成待确认卡后等待人类回复”这类跨请求挂起节点，必须画为明确的等待状态（如 `等待人类确认`）或清晰终止于 `◉` 并在复合状态外层标注新事件触发入口，严禁用无事件触发的实线直接跨轮连进落盘状态。

---

## 3. 面向业务决策者的直白表达原则

在遵循严格 UML 2.5 几何与语法规范的同时，图面文字与配套解释必须**去程序员黑话**（不直接裸写底层函数名、变量名或生僻算法术语），统一用直白准确的中文业务语言描述“在什么状态下、发生什么情况、满足什么条件、做什么动作”。
